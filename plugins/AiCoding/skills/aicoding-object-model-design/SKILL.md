# 对象模型设计

默认简体中文。围绕“哪些能力应成为独立对象，它们怎样协作并进入/退出运行”思考，具体对象、表示和管理机制从用例、变化与资源关系推导。

## Skill 类型

属于 `reusable-domain-knowledge` 与 `team-expertise`：沉淀对象设计概念与判断方法。

## 核心思路

- **对象**：具有职责、必要身份、状态、不变量和操作的协作单元；结构体、文件或线程的数量不能直接决定对象边界。
- **管理面与业务面**：生命周期管理回答怎样投入和退出运行，业务接口回答提供什么能力。存在共同管理需求时再统一前者，后者按实际语义设计。
- **设备与服务**：设备表达硬件能力，服务组织可复用系统能力；这是职责区分，未必对应固定基类、目录或执行上下文。
- **所有权与生命周期**：谁构造、连接、持有资源、改变状态和完成退出需要明确。对象布局与管理方式可以不同，但不能留下含糊的共享状态或在途访问。

## 设计时的思考路径

围绕会改变当前方案的问题选择性推导，不要求逐项产出表单：

- 什么需要独立变化、复用或测试？边界划在此处，比继续合并多解决了什么问题？
- 谁使用这项能力，需要看到哪些操作与状态？产品流程、能力实现与统一管理分别需要知道什么？
- 实例和资源的寿命是什么，依赖怎样影响启动、失败回退与退出完成？
- 普通模块、静态接线是否已足够？引入公共头、registry 或 manager 的收益与代价是什么？
- 哪个真实失败场景最能检验边界？用现有构建或小范围行为验证消除关键不确定性即可。

## 按需深入

确有统一管理需求，或要分析对象头、状态迁移、C 首成员嵌入时，读取[对象头与生命周期管理](references/object_lifecycle_zh.md)。

系统模块边界与依赖方向需要重新设计时，可结合 `aicoding-architecture`；内部字段、存储、访问与数据有效性成为主要问题时，可结合 `aicoding-data-model-design`。按实际缺口协作，已有上下文足以完成问题时直接处理，不将三个 Skill 必选串联或来回转交。

C 实现遵循项目规范并结合 `aicoding-c99-standard-c`；C++ 等工程复用身份、所有权与生命周期思想，不机械搬用 C 首成员布局。

## 验证与输出

输出当前对象边界、协作/生命周期选择、理由和必要验证。已确定的签名、布局等机械问题交给已有编译与检查；语义和取舍依据实际用例，未验证的硬件行为如实说明。

**必须考虑 App 层资产沉淀**：哪些产品对象、业务协作、生命周期约定及关键失败经验值得保留复用。沿用已有接口、测试和简短说明承载即可。
