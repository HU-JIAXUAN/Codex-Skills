# 函数与接口

## 触发与输入

函数、API、接口、参数、输入/输出、返回、回调、职责拆分或可测试性成为当前主问题时读取。输入是实际用例、已有接口/调用者、状态/资源归属和执行上下文；只改函数体时先确认要恢复或保持的合同。

## 设计流程

1. 用一个可观察动作描述函数的目的，区分业务处理、纯计算、硬件 I/O、状态推进和编排；先复用已有稳定能力。
2. 推导正常、边界、失败与退出路径，明确输入范围、单位、空指针、别名、实例就绪状态和必要前提。
3. 决定输出：无失败查询可以返回值；可能失败时区分错误与业务真假，说明输出参数/状态/硬件何时变化、失败是否保持。
4. 按“实例/上下文、输入、输出”组织参数，缓冲区与长度/容量相邻；只为稳定、内聚且寿命一致的参数组建结构体。
5. 确定可见性与依赖：公共声明放正式头文件，私有函数 `static`，内部前置声明集中；跨模块变化按架构入口判断边界。
6. 明确阻塞、可重入、ISR/任务上下文、回调注册期、保留指针和停止完成条件，按真实变化选择最小实现。
7. 写公共调用说明和关键实现意图，再对照真实调用者、编译与相称行为验证；已有授权和确认继续复用。

## 方法与取舍

- 用输入输出表和正常/失败例子推敲契约即可，不要求新建表单。先列会改变方案的事实，避免靠名称猜单位或失败策略。
- 校验、计算和状态提交在有独立意义时拆分；不要制造只转发一次的 helper，也不要让一个函数同时承担无关职责。
- 50 行、4 层、5 参数和较高扇出触发复核，结合时序、栈与算法内聚判断；不是自动拆分指令。
- 新公共 API 名表达模块、动作与对象，保持统一短前缀；不为改风格重命名稳定接口。
- 输出失败不改是常用策略，必须由实际代码实现；确需部分成功或清空输出时明确合同，不能套模板作假。

## 回调与异步接口

明确谁调用、何时/何种上下文调用、是否可重入、事件数据有效期、注册上下文寿命以及取消后何时不再到达。多实例使用各自上下文；不依赖临时栈对象或隐式全局槽。ISR 回调不能按任务函数方式等待/分配；停止返回不一定代表 DMA/回调已经排空。

## 注释与验收

公共声明写用途、输入、输出、返回和约束；定义解释必要实现原因，避免维护两份参数合同。逐项核对真实单位、失败输出、资源归属和上下文，而不是只数标签。
