# 命名与排版

## 触发与输入

命名、缩写、代码风格、缩进、大括号、行宽、formatter、格式整改或模板一致性成为主问题时读取。输入是当前用户要求、项目已确认基线、相邻自研代码、工具实际读取的配置及文件归属。

## 统一方法

1. 先确定一个有效基线；项目明确约定和当前用户要求优先，不能将示例前缀套给所有工程。
2. 按标识符职责选择风格：文件/函数 `snake_case`，参数/局部/字段 `lowerCamelCase`，类型 `PascalCase`，宏/枚举值 `UPPER_SNAKE_CASE`，文件状态 `g_` + lowerCamelCase。
3. 函数名表达模块、动作与对象，使用统一短前缀和明确动词，协议缩写保持一致；稳定公共 API 单独考虑兼容性。
4. 格式使用 4 空格、函数括号独行、控制块括号同行、默认 120 列；同一文件统一分区、普通注释和空行方式。
5. 让 formatter、lint、模板读取相同约定，先 dry-run 再处理需要的差异；不对第三方/生成代码或无关文件做整库格式化。

## 限制与取舍

- 名称形态可以部分机器检查；动词是否准确、缩写是否含糊、是否是拼音、参数是否内聚仍需语义判断。
- 32 字符、默认两个下划线、分词 12 字符等命名限制按项目约定和实际检查能力应用，不用重命名破坏稳定 ABI。
- `get/read/peek`、`set/write/update` 的区别由副作用决定，不把词表当成函数设计的替代品。
- 不用强转压告警、不关闭检查器、不用自动修复顺便改行为；编码和换行保护不由 formatter 自动保证。
- 复杂度信号引导职责复核，不为了数字拼参数包、制造碎片函数或新抽象层。

## 验收

确认本次实际文件与配置匹配、格式通过、接口调用者未受无关影响、注释/模板没有另一套风格；报告只检查格式还是同时执行了命名、安全和编译。
