# C99 安全与可移植性

先按实际用例、数据范围与目标约束推导实现，再用编译器、分析器和相称测试复核。以下 ID 用于审查和诊断定位，不表示这些规则都已自动实现；按任务检索[主题导航](topic-index-zh.md)。

## C99-SAFE-01：对象边界、容量和字符串

- 接口区分存储容量、当前有效长度与是否需要结束符。二进制数据携带长度，不用 `strlen`；字符串操作的前提是可达范围内确有 `\0`。
- 检查下标、偏移、元素个数和剩余容量后再形成或解引用指针。允许形成的 one-past 指针不可解引用；把指针转整数不能消除对象边界限制。
- 先确认 `offset <= capacity`，再比较 `length <= capacity - offset`；不要先算可能溢出的 `offset + length` 再比较。
- 保留终止符需要的空间。`strncpy` 不保证终止；`snprintf` 需处理负返回与截断，不能将其“期望写入长度”当作已经写入的字节数。
- `memcpy` 的源/目的不得重叠。可能重叠的移动使用 `memmove`，同时检查容量、索引、长度与指针寿命；改用 `memmove` 本身不证明这些条件成立。
- 不使用无界 `gets`；外部字符串不作为格式串。格式串由代码决定，并核对参数类型、数量和目标工具链格式支持。

## C99-SAFE-02：整数、表达式和移位

- 有符号整数溢出是未定义行为，不能拿某台机器的回绕输出当作算法；无符号回绕虽有定义，长度、索引、计时比较仍需证明符合业务意图。
- 加法在运算前比较 `right <= SIZE_MAX - left`；乘法先处理零，再比较 `count <= SIZE_MAX / elementSize`。不要先发生溢出再强转到宽类型。
- 缩窄前检查目标范围；有符号值转长度前检查负值。把 `atoi` 结果改成 unsigned 不能解决非法输入和范围问题；需要完整转换时检查解析终点与错误状态。
- 明确整型提升和 signed/unsigned 比较。不用强转来静默消除警告；先解释数据范围和转换含义。
- 移位前检查位数小于提升后左操作数的位宽，避免负移位数、有符号溢出和对负数右移的实现依赖。用目标类型的无符号掩码，不假定 `1U` 总有 32 位。
- 同一完整表达式中，不让对同一对象的多个副作用或读写依赖未规定的求值顺序。`foo(b += 3, ++b)` 不存在可移植的“正确输出”；拆成有明确顺序的语句并先确定用户需要的行为。
- 多语句宏用 `do { ... } while (0)`，参数及整个表达式适当括号化；多次求值的宏不得接收 `i++` 等有副作用实参，必要时改为函数或 `static inline`。

## C99-SAFE-03：寿命、类型与资源

- 不返回自动对象或临时缓冲区的悬空地址。释放后、注销后和停止未完成期间的访问都需检查，包括异步 DMA 与回调。
- 指针的类型、对齐和真实对象必须匹配；`magic`/`type` 字段不能证明任意地址有效。避免通过不兼容类型访问对象表示。
- 若需要查看对象表示，使用适当的字符类型访问并遵守范围；若需要复制类型表示，使用明确大小的 `memcpy` 并检查目标表示的有效性。
- `uintptr_t` 和精确宽度整数类型依赖目标实现是否提供；不要固定用 `uint32_t` 装指针，也不要把一个平台的 `sizeof` 和对齐写进通用接口。
- 动态分配只在项目允许的路径使用，检查大小和失败，明确释放者；`realloc` 先接临时指针，失败保留原资源。初始化失败只释放已经取得、且由本对象拥有的资源。
- 初始化/清理顺序与依赖对应。`memset(object, 0, ...)` 不能普遍替代指针、浮点或硬件对象的合法初始化。
- 不把标准库标识符重新定义成业务 API；公共头自包含，包含 guard 唯一，跨文件接口来自正式头文件，私有符号默认 `static`。

## C99-SAFE-04：协议、ABI 与平台

- C 的字节不自动等于 8 bit。检查 `CHAR_BIT`、目标 `sizeof` 单位、可用整数类型及外设搬运粒度；DSP/C28x 等目标不能机械照搬 PC 字节假设。
- 协议按明确的 octet、字段位宽与字节序编码/解析，不直接发送 native struct，也不把 `packed`、bit-field 或结构体强转当作跨平台协议定义。
- 不依赖 padding 内容、未初始化对象表示、native endianness、`long` 的固定大小或函数指针与数据指针互换。
- `const` 表示访问约束，不保证位于 Flash，也不保证没有可写别名。实际放置与 ABI 用链接文件、map、编译器约定和必要的布局检查证明。
- 严格 C99 与 C11/C++、编译器扩展分开。不要在 C99 代码中直接加入 `_Atomic`、`_Static_assert`、异常、`new/delete` 或 C++ stream；目标扩展必须明确且有实际编译证据。

## C99-SAFE-05：ISR、任务、DMA 与硬件

- 确认每个入口真实运行于 ISR、任务还是主循环，调用链中是否可能等待、分配、日志阻塞或使用不可重入库。
- `volatile` 不是互斥、完整快照或跨核发布协议；关中断也不自动解决 DMA、另一个核、cache 一致性或外设写缓冲。
- 明确唯一写入者、读者、原子访问宽度、发布顺序和缓冲区复用时机。时间戳、数据和质量位必须来自同一次可解释的发布。
- 实时路径的重试、等待与循环必须有上界及失败动作。设备/对象数量与线程数量分别设计；主机测试不能证明 WCET、中断延迟或采样窗口。
- 读取寄存器前查清读清、写 1 清零、只读/保留位和 RMW 副作用；不能对 W1C 状态寄存器机械使用 `|=`，也不能从寄存器命名推断时序。
- CPU 屏障、cache clean/invalidate、原子指令或临界区使用目标提供的正确原语；host stub 通过只证明该 stub 路径。

## C99-SAFE-06：验证与结果

至少覆盖当前风险相关的空输入、零长度、最大合法长度、刚超过边界、整数上下界、重复初始化/停止、失败回退及别名情况。无需对每次可逆小改动新建测试；复用已有行为用例和实际编译。

GCC/Clang 的严格告警、静态分析和可用的 host sanitizer 是互补证据。对 TI、IAR 等目标使用其等效诊断与真实构建，不把不兼容的 GCC 参数直接写入目标工程。关键设备交互、时序和并发还要板级证据。

语言合法性、工程风格与目标实现约束分别判断。不能把特定编译器扩展、某次运行结果或一次零告警当作通用语言保证。
