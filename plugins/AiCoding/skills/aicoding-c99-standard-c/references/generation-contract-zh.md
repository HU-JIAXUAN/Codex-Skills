# 生成与修改契约

目的：让实现来自用户的需求和当前工程，而不是来自模型习惯。小任务在回复和现有代码中说明即可，不要求新建需求表、设计文档或批准文件。

## 写入前确定的事实

| 项目 | 应从哪里取得 | 不允许自行补出的内容 |
|---|---|---|
| 行为 | 当前请求、既有接口和调用者、已有测试 | 成功条件、异常回退、单位和默认限值 |
| 修改范围 | 用户指定文件及真实调用/构建关系 | 趁机重命名公共 API、迁移所有字段或格式化全库 |
| 平台 | 工程配置、工具链、芯片和手册 | 假定所有目标都有 8 位字节、32 位 int、POSIX 或相同 ABI |
| 状态与资源 | 构造/初始化、调用链和退出路径 | 新的全局单例、隐含所有者、每对象一个任务 |
| 风格 | 项目 AGENTS、当前有效模板、相邻自研代码、用户要求 | 从旧参考恢复 Doxygen、历史表或陌生命名体系 |
| 验证 | 实际构建入口、已有工具、候选文件与配置 | 用演示代码通过代替当前文件通过，声称未运行的测试通过 |

已有会话中的明确授权、已定版接口和适用规则直接复用。用户让实现某个已清楚的功能，本身就是该范围的授权；只有确实存在会改变方案的缺失条件或未授权的公共契约变化才需要提问。

## 限制自由发挥的具体规则

1. 先读取现有实现及至少一个实际调用者，确认本次修复/功能的输入、输出、正常与失败行为。
2. 保持稳定公共 API、协议布局、单位、定时/中断边界及输出行为；这些确需变化时明确列出影响，再依据当前授权推进。
3. 新能力用当前工程已有接口连接。没有依据的 SDK API、寄存器位、外设时序不得写成可用实现；缺失点要具体说明。
4. 仅为当前变化、状态归属或必要测试建立边界。模块化、平台适配与解耦必须先加载 `aicoding-architecture`，不预设 manager、ops、线程或固定层数。
5. 参数初始化与运行状态复位分清；谁写入运行状态、何时发布结果、停止后是否仍有回调必须明确。遥测读真实运行来源，不再维护一份影子状态。
6. 不为了减少参数或函数行数而机械包装。保持参数内聚、失败输出一致和可解释的副作用；50 行/4 层/5 参数首先触发设计复核。
7. 只读输入指针用 `const`；缓冲区带容量/有效长度；指针是否保留、允许的别名、单位、错误和有效期必须能由接口或相邻说明确定。
8. 保留实际编码、BOM、换行和生成/第三方边界。所有转换独立列入差异；不把 formatter 的成功当作编码保持证明。
9. 禁止用 `TODO`、空实现、恒定成功、吞掉返回值或假硬件值冒充已完成功能。用户明确只要骨架时标明未实现路径及其可观察行为。
10. 不擅自关闭 warning、删测试、改规则严重度、扩大排除目录或更新 baseline 来消除本次失败。环境缺工具、配置不兼容、旧代码已有问题分别报告。
11. 实现后逐项对照当前契约，检查受影响调用者与头文件；复用已有构建与相称的行为验证，不添加只复述实现的测试。
12. 收尾报告实际修改、所用规范/配置、检查对象与结果、人工/目标板未验证项。失败、未运行、仅通过演示分别说明。

## 最小接口复核

实现一个可能失败的接口前，应能回答：

- 参数是否合法由谁检查，哪些参数可空，长度与容量是否分开？
- 正常结果何时有效，失败是否会部分修改输出或状态？
- 资源由谁持有，返回以后调用者是否仍能使用它，何时能释放或复用？
- 是否阻塞、是否允许 ISR 调用、是否可重入、最坏执行时间的证据是什么？
- 新行为怎样通过现有调用者观察，当前最小验证能消除哪个风险？

这些问题指导实现和审查，不强制输出固定表单。字段或对象设计出现实质缺口时，由架构 Skill 路由相应内部指南。

## 检查记录的真实性

检查记录至少能定位到实际候选文件、当前内容、使用的配置、命令与退出状态。修改文件或配置后，旧通过结果失效；只检查了部分文件时不能声称整个工程通过。Hook 给出的“命令退出 0”也只证明该命令覆盖的规则，不能证明需求、内存安全或时序完全正确。

详细工具范围和 Hook 行为见[验证与 Hook](verification-and-hooks-zh.md)。
