# 架构成熟度与证据分级

本文件帮助判断架构实际落地了什么、证据能支持什么结论，以及常见误判怎样避免。成熟度描述仅供需要正式评估的项目选用，不是每次设计的评分要求。判断依据引用[架构原则](architecture_principles_zh.md)，约束引用[依赖规则与门禁](dependency_rules_and_gates_zh.md)，角色引用[语义层级模型](semantic_layer_model_zh.md)，方法引用[架构方法](architecture_methods_zh.md)，结构名称引用[模式目录](architecture_patterns_zh.md)，可观察信号引用[泄漏信号与基线测量](leak_signals_and_baseline_zh.md)。本文件不重复它们的定义。

<a id="SYN-001"></a>
### SYN-001 成熟度阶梯

```text
L0 生成基线：芯片、SDK、OS 可以构建
L1 职责清楚：模块的行为、变化原因和关键资源归属可解释
L2 契约隔离：调用者通过稳定接口使用能力，无需掌握无关环境细节
L3 构建隔离：public/private 与依赖方向由构建系统和 lint 限制
L4 组合清楚：实例、依赖绑定和生命周期有明确归属，变化影响可控
L5 持续验证：项目选定的关键架构约束有可重复检查
```

这些描述是观察维度，不要求项目逐级采用同一套结构。若使用等级报告，应先说明本项目的判据与适用范围，并提供相称证据；适合机械检查的约束可按 [AM-006](architecture_methods_zh.md#AM-006) 自动化。目录、命名和文档本身不能证明实现完成。

<a id="SYN-002"></a>
### SYN-002 成熟度不能按目录评分

分层命名、`Platform` 目录、`Port`/`Wrapper` 文件名和架构说明文档都只表达候选边界。结合 [AP-008](architecture_principles_zh.md#AP-008) 检查本次相关的逻辑、运行和构建事实，按 [DR-013](dependency_rules_and_gates_zh.md#DR-013) 区分 planned 与 implemented。未接入构建的骨架不能计为已落地能力。

<a id="SYN-003"></a>
### SYN-003 边界需要实际行为与依赖证据

判断解耦要看接口是否隐藏无关细节、状态与资源是否有归属、依赖是否符合设计，以及真实变化是否被限制在预期范围。普通函数或静态绑定也能满足这些目标；适配器、替身与集中装配在有收益时选用，可参考 [PAT-002](architecture_patterns_zh.md#PAT-002)、[PAT-006](architecture_patterns_zh.md#PAT-006) 和 [PAT-007](architecture_patterns_zh.md#PAT-007)。不要求每个组件同时具备这些模式。

<a id="SYN-004"></a>
### SYN-004 起步方式取决于项目状态

新项目避免铺满无用占位，存量项目避免一次重写全部层次。需要新骨架时参考 [AM-004](architecture_methods_zh.md#AM-004)，优先用 [AM-005](architecture_methods_zh.md#AM-005) 验证真实变化点；存量迁移参考 [AM-007](architecture_methods_zh.md#AM-007)，只有需要比较趋势时再用 [AM-010](architecture_methods_zh.md#AM-010) 建立基线。

<a id="SYN-005"></a>
### SYN-005 模式识别必须区分证据强度

Factory、Registry、状态机等名称只有在代码结构和职责同时吻合时才能使用。资源表与注册函数可以证明 [PAT-008](architecture_patterns_zh.md#PAT-008) 或 [PAT-021](architecture_patterns_zh.md#PAT-021) 的结构特征，却不自动证明 [PAT-009](architecture_patterns_zh.md#PAT-009)；空目录两者都不能证明。常见误判信号见 [SIG-007](leak_signals_and_baseline_zh.md#SIG-007)。

<a id="SYN-006"></a>
### SYN-006 先归一语义，再讨论层级

不同 SDK、教材和团队对 `Core`、`Device`、`Platform` 的含义不一致。依据 [AP-009](architecture_principles_zh.md#AP-009) 和 [AM-009](architecture_methods_zh.md#AM-009)，先理解实际职责，再检查依赖；正式审计或工具扫描需要时再维护角色 ID 映射。厂商命名不能代替职责判断。命名与角色不一致的可观察信号见 [SIG-001](leak_signals_and_baseline_zh.md#SIG-001)。

<a id="SYN-007"></a>
### SYN-007 区分 Device 链路中的变化原因

分析外部器件链路时，可从设备服务、器件协议、板级绑定和 MCU/OS 机制识别变化原因。它们可以共处于一个文件或目录；是否形成独立模块取决于实际变化、复用和维护成本，依据见 [DR-015](dependency_rules_and_gates_zh.md#DR-015)。

<a id="SYN-008"></a>
### SYN-008 解耦同时包含资源与时间契约

函数接口需要与其使用条件一起理解。资源 owner、执行上下文、超时、失败与恢复责任中，凡影响调用正确性的部分都应清楚，依据见 [DR-007](dependency_rules_and_gates_zh.md#DR-007) 与 [DR-011](dependency_rules_and_gates_zh.md#DR-011)。已有接口说明足够时直接复用，不为每个模块补齐无关字段。

<a id="SYN-009"></a>
### SYN-009 C 技巧不是架构本身

函数指针表、回调、宏和动态内存可以实现模式，但不能代替变化分析。函数指针表可能是 Port/Strategy，也可能只是间接调用；静态对象同样可以完成依赖注入。模式判定以职责和选择权为准，而不是语法形状。

<a id="SYN-010"></a>
### SYN-010 结论必须按证据分级报告

依据 [AP-010](architecture_principles_zh.md#AP-010)，区分以下证据强度；有必要时用表格或标签表达，无需逐句套格式：

| 级别 | 允许的依据 | 不允许的表述 |
|---|---|---|
| 已验证事实 | 命令、文件位置、构建日志、测试输出、硬件测量 | 用目录名或命名约定作为依据 |
| 有根据推断 | 职责、依赖和类型证据支撑的判断 | 写成“已解耦”“已平台化” |
| 未验证假设 | 需要目标板或未执行的测试 | 计入完成度或发布结论 |

“静态检查通过”不等于“硬件验证通过”；“目录已分层”不等于“依赖已隔离”。缺少同级别证据时，只能降级表述，不得升级。

<a id="SYN-011"></a>
### SYN-011 评估时的思考问题

| 提问 | 需要进一步理解的内容 |
|---|---|
| 职责与资源归属是否清楚？ | 重叠、空缺和多 owner 是否是有意协作 |
| 公共接口是否隐藏了调用者无关的实现细节？ | 环境类型暴露是否来自真实调用需求 |
| 边界收益是否有证据？ | 可用受控替换、局部构建、行为回归或变化影响分析 |
| 构建可见性是否符合预期依赖？ | 是否存在误包含或链接依赖扩散 |
| 绑定与生命周期由谁负责？ | 创建、启动、停止与失败回收是否一致 |
| 哪些约束值得持续检查？ | 自动化收益是否覆盖维护成本 |

问题用于定位风险和改进方向，不因缺少 Fake、映射表或单一装配文件机械封顶。项目采用正式门禁时，另按已声明的适用规则判断通过与否。

<a id="SYN-012"></a>
### SYN-012 架构成熟度与复用范围分别说明

架构评估不能代替具体成果的适用说明。**App 资产沉淀必须考虑**，包括产品流程、业务规则、状态机、数据模型、异常处理和经验；成果可以服务于同一产品族，平台适配可以限定 MCU/SDK。简要保留可复用内容、入口与验证范围，不强制资产等级、共享库或第二项目证明。
