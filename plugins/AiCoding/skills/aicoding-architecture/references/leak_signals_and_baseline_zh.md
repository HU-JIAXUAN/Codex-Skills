# 泄漏信号与基线测量

本文件只定义“怎样在任意固件仓库里发现边界失效的可观察信号，并把它变成可复现数值”。信号本身不是缺陷判定：判定依据在[依赖规则与门禁](dependency_rules_and_gates_zh.md)，角色归属在[语义层级模型](semantic_layer_model_zh.md)，执行步骤在[架构方法](architecture_methods_zh.md)，结构命名在[模式目录](architecture_patterns_zh.md)。

这些信号用于选择观察点，不要求每次任务做全库统计。所有命令都是模式模板，使用时按实际构建系统、语言、目录和角色替换占位符；项目路径和数值保留在项目记录中。

<a id="SIG-001"></a>
### SIG-001 目录名与角色不一致

可观察信号：

```text
同一目录内既有产品策略又有寄存器访问
名为 Platform/Port/Interface 的文件公共头包含厂商类型
名为 Common/Utils 的目录承载状态机或产品判断
名为 Service/Server 的模块直接持有外设句柄
同一能力在两个不同顶层目录各有一份实现
```

处理方式：按 [AM-009](architecture_methods_zh.md#AM-009) 核对相关模块的实际职责；需要正式自动审计时再记录角色映射，按 [GATE-009](dependency_rules_and_gates_zh.md#GATE-009) 处理未分类模块。局部分析不要求先完成全库映射。

测量项：未分类模块数、承担多个主要角色的模块数、同一角色分布的目录数。

<a id="SIG-002"></a>
### SIG-002 公共契约泄漏环境类型

可观察信号：公共头中出现厂商句柄、寄存器结构、RTOS 对象、供应商枚举或生成代码类型；或产品侧模块直接包含 SDK/内核头。

测量模板：

```text
对每个角色区域 R，统计直接包含 <厂商头模式|RTOS 头模式|生成头模式> 的源文件数
对每个 Port 公共头，单独编译（不引入任何环境头）并记录失败数
```

判定：产品意图、应用编排、领域算法和能力契约区域的计数应为 0，对应 [DR-003](dependency_rules_and_gates_zh.md#DR-003)、[DR-006](dependency_rules_and_gates_zh.md#DR-006)，门禁为 [GATE-002](dependency_rules_and_gates_zh.md#GATE-002)。

<a id="SIG-003"></a>
### SIG-003 全局可见性代替受控可见性

可观察信号：构建工程使用一条包含大量条目的全局 include 搜索路径，使任意源文件都能看到全部头文件；或所有组件共用同一个 include 根。

测量项：全局 include 搜索路径条数；能被产品侧看见但不属于其允许依赖的公共头数量。

判定：按 [DR-008](dependency_rules_and_gates_zh.md#DR-008) 检查不必要的可见性，构建通过本身不能证明依赖受控。可按影响逐步收紧，检查参考 [GATE-003](dependency_rules_and_gates_zh.md#GATE-003)，不以全库构建改造作为讨论边界的前提。

<a id="SIG-004"></a>
### SIG-004 能力重复与 owner 缺失

可观察信号：同一 OS 适配、同一器件驱动或同一配置在多个路径各有一份；或两个模块的职责句子高度相似；或一份资源出现多个写入方。

测量项：重复能力组数、无 owner 资源数、多 owner 资源数。

判定：按 [DR-001](dependency_rules_and_gates_zh.md#DR-001) 核对是否确为同一能力，以及实际构建、维护和资源 owner 是否冲突。确有重复时明确来源与选择权，不能仅凭多目录断言所有度量失效或阻断无关调整。

<a id="SIG-005"></a>
### SIG-005 占位与弱实现被计入完成度

可观察信号：

```text
弱符号默认实现的函数体为死循环、空体或直接返回成功
配置表中存在被注释掉的条目
目录或组件已建立但未进入任何构建目标
架构说明中的组件在组合根里没有对应实例
```

测量项：planned 组件数、弱实现占位数、未进入构建的组件数、声明有而构建无（及反向）的差异数。

判定：违反 [DR-016](dependency_rules_and_gates_zh.md#DR-016) 与 [DR-013](dependency_rules_and_gates_zh.md#DR-013)。这些条目必须显式列为未落地，不得计入完成度；缺失依赖时的行为必须可观测，门禁为 [GATE-008](dependency_rules_and_gates_zh.md#GATE-008)。

<a id="SIG-006"></a>
### SIG-006 组合职责分散

可观察信号：实例创建、注册和启动分散在多个初始化函数、多个任务入口或各模块自身的 init 中；使用者通过全局变量或 locator 获取依赖。

观察实例创建/注册是否有清楚归属、普通业务使用者是否依赖具体实现；多个组装函数可以属于同一个明确的启动设计，不按函数或文件数量判错。

判定：违反 [DR-004](dependency_rules_and_gates_zh.md#DR-004)。目标结构见 [PAT-007](architecture_patterns_zh.md#PAT-007)，注入方式见 [PAT-006](architecture_patterns_zh.md#PAT-006)。

<a id="SIG-007"></a>
### SIG-007 结构特征被当作时序与正确性证据

可观察信号：以“存在固定节拍任务”“存在状态表和 Enter/Run/Exit”“存在函数指针表”作为实时性、健壮性或解耦已达成的结论。

处理方式：结构特征只能证明采用了 [PAT-016](architecture_patterns_zh.md#PAT-016)、[PAT-012](architecture_patterns_zh.md#PAT-012) 或 [PAT-021](architecture_patterns_zh.md#PAT-021) 的形态。周期是否满足预算必须由目标板测量，非法事件与超时是否覆盖必须由状态迁移测试证明，间接调用是否构成 Port 必须由公共类型和选择权证明。

测量项：已测量的最坏执行时间与抖动、状态迁移测试覆盖的迁移数与非法事件数，门禁为 [GATE-005](dependency_rules_and_gates_zh.md#GATE-005) 与 [GATE-004](dependency_rules_and_gates_zh.md#GATE-004)。

<a id="SIG-010"></a>
### SIG-010 已存在的契约层被误判为实现层

最容易犯的一类错，且工具默认不会提醒：把一个**已经承担契约职责**的目录整体判成实现层，于是后续所有依赖它的模块都被报成越界。

可观察信号：

```text
一条映射规则同时盖住"公共头全部环境中立"和"源文件直接接触环境"
被判为实现层的目录里，公共头不含任何厂商类型
提出的改造方案是给一个本来就中立的接口再包一层
上层对它的依赖被大量报成违规，但改法说不出隔离了什么变化
```

处理方式：按 [AM-011](architecture_methods_zh.md#AM-011) 先测公共头的环境中立性，再判角色。头与源分处不同子目录且中立性相反时，那就是已经存在的契约层与实现层，按 [DR-014](dependency_rules_and_gates_zh.md#DR-014) 分开映射。

判定代价：误判方向是"凭空多出一批违规"，很容易被当成真实债务去修，从而引入 [DR-012](dependency_rules_and_gates_zh.md#DR-012) 意义上的投机抽象。**包装一个本来就中立的接口，不隔离任何环境类型，只增加间接层。**

<a id="SIG-011"></a>
### SIG-011 检查结果建立在残缺的判断输入上

可观察信号：检查通过、数字漂亮，但配置里"什么算环境头""什么算环境类型""谁确认的角色映射"是空的。

报告“0 违规”时，说明依据哪些角色和规则、扫描覆盖什么范围，环境模式是否对应实际 SDK。配置缺失不能算通过；采用本检查器做阻塞检查还需满足其确认字段，但不把该条件推广为所有架构分析的审批要求。

工具侧的对应做法是：判断输入缺失时拒绝给出结论并返回非零，而不是报 0。

<a id="SIG-008"></a>
### SIG-008 基线记录格式

按 [AM-010](architecture_methods_zh.md#AM-010) 执行时，每个指标必须同时记录命令、快照标识和数值，否则不可比：

| 指标 | 命令模板 | 快照（分支/提交/工作树状态） | 数值 | 目标值 |
|---|---|---|---|---|
| 未分类模块数 | `<填写>` | `<填写>` | `<填写>` | 0 |
| 各角色区域的环境头包含文件数 | `<填写>` | `<填写>` | `<填写>` | 产品侧为 0 |
| 全局 include 搜索路径条数 | `<填写>` | `<填写>` | `<填写>` | `<受控值>` |
| 重复能力组数 | `<填写>` | `<填写>` | `<填写>` | 0 |
| planned／弱实现占位数 | `<填写>` | `<填写>` | `<填写>` | `<显式清单>` |
| 组合位置数 | `<填写>` | `<填写>` | `<填写>` | 1 |

注明工作树状态及统计范围，避免把不同输入直接比较。趋势目标按项目采用的规则决定；局部分析无需建立趋势台账，一次静态基线也不能单独证明可发布。

<a id="SIG-009"></a>
### SIG-009 第一个切片的选点规则

在多个泄漏区域中，可参考以下线索选择 [AM-005](architecture_methods_zh.md#AM-005) 的纵向切片，不要求同时满足：

```text
泄漏计数最高，收敛后基线变化可见
已存在候选 Port 命名或候选契约，改造量可控
存在真实的第二实现、器件变体或故障注入需求
核心判定逻辑可以移出执行上下文并在主机侧运行
```

切片的价值在于用可控改动检验边界是否限制了变化传播。选择与当前问题相称的验证，不以第二实现、主机测试或独立替身作为所有切片的成立条件。
