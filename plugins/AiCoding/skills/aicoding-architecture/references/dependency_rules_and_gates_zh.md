# 嵌入式依赖规则与架构门禁

本文件是边界约束和门禁的唯一规范来源。原则依据来自[架构原则](architecture_principles_zh.md)，判层角色来自[语义层级模型](semantic_layer_model_zh.md)。其他文件只能按 ID 引用这里的规则，不复制规则正文。

## 规范用语

“必须”表示架构约束；“应”表示默认选择，偏离时需要记录理由；“可以”表示可选机制。规则是否适用由项目架构说明声明，但一旦选用，不应在模板或检查表中改写其含义。App 与环境细节解耦是核心要求，具体组织形式和检查方式按项目需要选择。

<a id="DR-001"></a>
### DR-001 职责与所有权唯一

每个模块必须声明一个主要职责、明确非职责，并为其可变状态和资源指定唯一所有者。跨模块不得直接写入他方私有状态。

<a id="DR-002"></a>
### DR-002 源码依赖只能指向内层稳定契约

一种符合原则的依赖示例（不是强制目录或层数）：

```text
产品意图 / 应用编排（App） -> Service 公共业务契约 <- Service 实现 / 领域
Service 实现 / 领域 -> Platform 能力契约 <- MCU/OS 实现 -> Vendor
器件协议 ----------> 总线 / IRQ / 时间契约 <--- MCU/OS 实现
          组合与板级绑定负责选择并连接实现
```

允许关系按“源码 include、符号链接和类型可见性”判断，而不是按运行时调用方向判断。下表按角色说明依赖原则，不要求工程采用固定层数或固定命名；结合实际公共接口判断，不能仅凭角色 ID 声称解耦。

| 调用方 | 允许依赖 | 禁止直接依赖 |
|---|---|---|
| [SL-001 产品意图](semantic_layer_model_zh.md#SL-001) | [SL-002](semantic_layer_model_zh.md#SL-002)、稳定业务/领域接口与能力契约（SL-003/SL-004） | 器件、板级、MCU/OS、外部代码 |
| [SL-002 应用编排](semantic_layer_model_zh.md#SL-002) | 稳定业务/领域接口与能力契约（SL-003/SL-004） | 器件实现、板级、MCU/OS、外部代码 |
| [SL-003 领域／算法](semantic_layer_model_zh.md#SL-003) | [SL-004](semantic_layer_model_zh.md#SL-004)、纯 [SL-009](semantic_layer_model_zh.md#SL-009) | 器件实现、板级、MCU/OS、外部代码 |
| [SL-004 能力契约](semantic_layer_model_zh.md#SL-004) | 语言基础类型、稳定值对象 | 厂商 SDK、RTOS、寄存器、具体实现 |
| [SL-005 器件协议](semantic_layer_model_zh.md#SL-005) | [SL-004](semantic_layer_model_zh.md#SL-004)、可移植 [SL-009](semantic_layer_model_zh.md#SL-009) | 具体 MCU/OS 句柄、产品私有实现 |

<a id="DR-003"></a>
### DR-003 公共 Port 保持环境纯净

公共 Port 的参数、返回值、错误码和结构体必须使用项目稳定类型，不得暴露寄存器结构、HAL 句柄、RTOS 对象、供应商枚举或生成代码类型。环境特有类型只能出现在实现侧或私有头文件。

<a id="DR-004"></a>
### DR-004 具体实现只在组合根可见

实现选择、实例创建和启动接线应有可识别的归属，避免散落到普通业务使用者中。可以采用现有启动函数或组合模块；不要求新增容器、注册框架或单独目录。普通业务使用者不应依赖具体实现细节或隐式全局查找。

<a id="DR-005"></a>
### DR-005 状态与资源禁止隐式共享

可变全局状态、外部可写 `extern`、匿名共享缓冲区和跨层裸句柄不得作为协作机制。共享数据必须通过所有者提供的契约访问，并声明生命周期、同步方式和失败语义。

<a id="DR-006"></a>
### DR-006 环境能力通过边界隔离

时间、调度、总线、存储、日志、随机数和设备 I/O 等环境能力应通过 Port 或窄适配层提供。核心策略不得依赖特定 RTOS/HAL 的调用方式。

<a id="DR-007"></a>
### DR-007 执行上下文属于接口契约

公共操作明确影响调用者的上下文、阻塞、并发和 ISR 限制。强实时操作需要可判断的执行预算；ISR 工作保持有界，需要延后处理时采用明确交接，不预设 RTOS 或固定任务模型。

<a id="DR-008"></a>
### DR-008 可见性由构建系统实施

每个组件必须区分 public/private 头文件与源文件；构建目标只导出必要 include 路径。不得依靠全局 include 搜索路径让任意层看到所有头文件，组件依赖图不得成环。

<a id="DR-009"></a>
### DR-009 Vendor 与 Generated 代码隔离

供应商库和生成代码应位于明确隔离区。手写核心代码不得直接依赖其类型；升级时只允许修改隔离区、适配器和必要的组合配置。

<a id="DR-010"></a>
### DR-010 配置按变化域归属

构建配置、板级资源配置、产品策略配置和运行时持久参数必须分域管理。配置的 owner、生成来源、默认值、校验和生效时机必须明确，不得用一个全局配置头承载所有变化。

<a id="DR-011"></a>
### DR-011 错误与可观测性跨层保留语义

边界必须定义稳定错误语义，并明确重试、降级、上报和恢复责任。适配器负责把底层错误映射为契约错误；不得静默吞错，也不得把供应商错误码直接泄漏到高层。

<a id="DR-012"></a>
### DR-012 新抽象必须通过准入问题

引入接口、工厂、注册表或事件总线前，考虑真实变化轴、选择权、测试或替换收益，以及间接层代价。第二实现或测试替身可以提供依据，但不是准入数量要求。收益不清时保持直接设计；已有稳定公共接口可以直接复用。结构简化仍应保持 DR-017 的业务边界。

<a id="DR-013"></a>
### DR-013 语义、构建和运行视图必须一致

架构声明中的组件必须在构建目标、include 可见性和 Composition Root 中有对应关系；尚未实现的目录或模块必须显式标记为 planned，不得计入已落地能力。构建中存在但架构声明缺失的组件同样属于漂移。

<a id="DR-014"></a>
### DR-014 模块按语义角色而非目录名判层

分析相关模块的职责和主要变化原因，不得因路径名为 `Core`、`Device`、`BSP`、`Platform` 或 `Middleware` 就自动允许或禁止依赖；同一目录中的模块可以承担不同角色。需要自动分层检查时，再把已分析的角色写入对应映射。

<a id="DR-015"></a>
### DR-015 外部器件协议与 MCU/板级绑定分离

外部器件的寄存器、命令和状态逻辑必须依赖总线、IRQ、时间等稳定能力契约；具体 MCU 句柄、总线实例、地址、片选、引脚和供电绑定只允许存在于 MCU 机制、板级绑定或组合配置。固定且无复用价值的小实现可以物理合并，但公共契约不得泄漏环境类型。

<a id="DR-016"></a>
### DR-016 占位与弱实现必须可区分

`__WEAK` 默认实现、空实现、Null Object 和 planned 占位可以用于分阶段接线，但必须能被机器区分并计入未落地清单。缺失真实实现时不得静默进入死循环或静默返回成功，也不得在完成度统计中计为已实现。

<a id="DR-017"></a>
### DR-017 App 与具体机制解耦

App 关注产品要做什么，通过职责明确的业务接口使用系统能力，避免让产品流程直接依赖 HAL、寄存器、具体 OS 对象或器件实现。Service 是组织可复用系统能力的一种方式，不能把层名和固定调用链当作解耦本身。

模块通过公共接口、命令、事件或明确约定的数据协作，不越权修改其他模块私有状态。数据与错误表达稳定语义，资源绑定和实现选择留在适当的适配/组合位置。

固定硬件、裸机与强实时同样应保持职责边界；可以采用普通函数、静态绑定或内联。根据实际变化点与验证需要选择最小边界，不强制每个模块都有 Port、Adapter、Fake 或单独目录。

<a id="DR-018"></a>
### DR-018 对象、数据和生命周期保持一致

对象由职责、身份、协作与不变量定义，不以结构体、函数表或线程的存在作为判据。状态和资源应有明确所有者与寿命，跨模块契约保持一致，不能让两份可独立修改的状态同时充当真实来源。

身份、实例协作和生命周期的细化按需读取[对象模型子指南](../object-model-design/GUIDE.md)；字段语义、类型、读写权限与表示取舍按需读取[数据模型子指南](../data-model-design/GUIDE.md)，统一由 `aicoding-architecture` 路由。本规则只维护跨模块一致性，不重复规定对象头、状态枚举或 `cfg/ctx/data/ops` 布局。

<a id="DR-019"></a>
### DR-019 工程开发必须考虑 App 资产沉淀

开发前查看已有可复用成果，设计和实现中主动隔离项目偶然细节；工程收尾必须考虑 App 层的产品流程、状态机、业务规则、数据模型和异常处理经验怎样保留与复用，也关注服务、算法、验证工具、架构决策与平台适配。

沉淀以能被后续使用为目标：保留清楚的职责与接口、实际来源、最小用法、验证入口和必要限制。App 成果可以只面向同产品族；平台适配可以限定芯片和 SDK，不要求所有成果都成为跨平台公共库。

优先复用已有代码、测试和项目说明，简要交代沉淀了什么、后续怎样使用和验证。按实际证据说明适用范围，不强制资产分级、台账、第二项目证明或新仓库；复用后的修正尽量回到同一维护来源。

## 架构门禁

<a id="GATE-001"></a>
### GATE-001 依赖方向检查

由 include/layer lint 或编译目标关系检查禁止依赖和组件环；新增违规必须使 CI 失败。

<a id="GATE-002"></a>
### GATE-002 公共头文件纯度检查

扫描 public 头文件中的环境特有类型和禁止 include，并对每个 Port 做独立编译检查。

<a id="GATE-003"></a>
### GATE-003 组件可见性检查

构建系统只暴露声明过的 public include 和显式链接依赖；用组件图检查越层依赖与循环依赖。全局 include 搜索路径数量应有上限并纳入趋势观察。

<a id="GATE-004"></a>
### GATE-004 替身与主机测试

对本次受影响的策略选择有意义的行为验证，包括适用的失败与恢复路径。可复用主机测试或按需使用 Fake/Stub；不要求每个模块新增替身。需要独立验证的策略不应被无关的目标板全局初始化绑住。

<a id="GATE-005"></a>
### GATE-005 资源与时序预算检查

对任务栈、静态内存、队列深度、ISR 时长、周期抖动和最坏执行时间建立预算及测量证据。超预算必须阻断发布或有正式豁免。

<a id="GATE-006"></a>
### GATE-006 发布与升级检查

供应商库、生成代码、板级配置或接口契约变更时，按影响选择构建、静态、兼容性与回归检查。涉及实际硬件行为或时序的结论需要相应目标证据；未执行不能标为通过，也不把目标板回归强加给无关改动。

<a id="GATE-007"></a>
### GATE-007 文档架构检查

文档清单、职责所有权、依赖无环、链接与声明依赖一致、锚点有效、规则 ID 唯一归属和引用完整性必须由仓库内脚本校验。

<a id="GATE-008"></a>
### GATE-008 三视图一致性检查

将架构组件清单与构建目标/源文件清单、public/private include 关系及 Composition Root 实例图进行比较；未接线、未声明或越权可见的差异必须失败或具有正式例外。

<a id="GATE-009"></a>
### GATE-009 语义层级映射检查

维护“实际路径/构建目标 -> 语义角色 -> 允许依赖角色”的机器可读映射。依赖扫描必须按角色而非厂商目录名报告违规文件、来源角色和目标角色，并对未分类模块返回失败。

<a id="GATE-010"></a>
### GATE-010 量产与升级门禁

镜像校验、版本与构建标识、Bootloader/App 边界、断电恢复、回滚、防降级、参数与校准区保护以及产线追溯必须有可复现的验证步骤，缺失时阻断发布打包或产线包生成。

<a id="GATE-011"></a>
### GATE-011 解耦效果检查

按当前改动选择必要证据：真实调用/include 与公共类型、构建可见性、状态归属，以及受影响的行为测试。关键判断是业务是否仍依赖具体环境细节、变化是否被限制在合理边界，不能用层名、改名或扫描零违规代替分析。

可以使用隔离构建、Fake 或符号检查，但不要求每次改动全部执行，也不规定 App 只能包含某个目录。验证与本次范围和风险相称；实时性能用对应目标测量，未执行项如实说明。

## 机器化要求

能由已有构建、静态扫描或测试稳定判断的约束，优先交给工具。仅在项目确有持续执行需要时新增自动检查，明确判定条件和执行入口；作为阻塞门禁时还应明确阶段，并输出可定位的信息和失败退出码。

普通设计分析不要求为每个边界编写检查器、Hook 或审批记录。模块职责、变化原因和抽象代价仍由用例与代码证据支撑，不能靠规则数量代替判断。

## 落地状态声明

`scripts/validate_document_architecture.ps1` 实现本 skill 自身的 [GATE-007](#GATE-007)；`scripts/check_layering.ps1` 对目标工程的 GATE-001、GATE-002、GATE-009 提供基于已确认映射和文本模式的部分检查。它不解析符号调用、真实构建可见性和私有状态写入，也不保证 include 解析完整。GATE-011 以及其余适用门禁按目标工程实际构建、测试与硬件平台选择落地；不能凭本文件或一次扫描零违规判定已实现。
