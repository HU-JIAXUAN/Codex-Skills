# 嵌入式依赖规则与架构门禁

本文件是边界约束和门禁的唯一规范来源。原则依据来自[架构原则](architecture_principles_zh.md)，判层角色来自[语义层级模型](semantic_layer_model_zh.md)。其他文件只能按 ID 引用这里的规则，不复制规则正文。

## 规范用语

“必须”表示架构约束；“应”表示默认选择，偏离时需要记录理由；“可以”表示可选机制。规则是否适用由项目架构说明声明，但一旦选用，不应在模板或检查表中改写其含义。

<a id="DR-001"></a>
### DR-001 职责与所有权唯一

每个模块必须声明一个主要职责、明确非职责，并为其可变状态和资源指定唯一所有者。跨模块不得直接写入他方私有状态。

<a id="DR-002"></a>
### DR-002 源码依赖只能指向内层稳定契约

默认依赖方向为：

```text
产品意图 -> 应用编排 -> 领域/算法
     \          |          /
          稳定能力契约
器件协议 ------> 契约 <------ MCU/OS 实现 -> 外部代码
          组合与板级绑定负责选择并连接实现
```

允许关系按“源码 include、符号链接和类型可见性”判断，而不是按运行时调用方向判断。

<a id="DR-003"></a>
### DR-003 公共 Port 保持环境纯净

公共 Port 的参数、返回值、错误码和结构体必须使用项目稳定类型，不得暴露寄存器结构、HAL 句柄、RTOS 对象、供应商枚举或生成代码类型。环境特有类型只能出现在实现侧或私有头文件。

<a id="DR-004"></a>
### DR-004 具体实现只在组合根可见

实现选择、实例创建、依赖注入、注册顺序和生命周期启动必须集中在一个可识别的 Composition Root。普通使用者不得包含具体实现头文件、调用全局 locator，或自行执行注册。

<a id="DR-005"></a>
### DR-005 状态与资源禁止隐式共享

可变全局状态、外部可写 `extern`、匿名共享缓冲区和跨层裸句柄不得作为协作机制。共享数据必须通过所有者提供的契约访问，并声明生命周期、同步方式和失败语义。

<a id="DR-006"></a>
### DR-006 环境能力通过边界隔离

时间、调度、总线、存储、日志、随机数和设备 I/O 等环境能力应通过 Port 或窄适配层提供。核心策略不得依赖特定 RTOS/HAL 的调用方式。

<a id="DR-007"></a>
### DR-007 执行上下文属于接口契约

公共操作必须说明可调用上下文、是否阻塞、最大执行时间、并发安全性和 ISR 限制。ISR 只做有界工作，并通过显式交接机制把非实时工作移交线程或事件循环。

<a id="DR-008"></a>
### DR-008 可见性由构建系统实施

每个组件必须区分 public/private 头文件与源文件；构建目标只导出必要 include 路径。不得依靠全局 include 搜索路径让任意层看到所有头文件，组件依赖图不得成环。

<a id="DR-009"></a>
### DR-009 Vendor 与 Generated 代码隔离

供应商库和生成代码应位于明确隔离区。手写核心代码不得直接依赖其类型；升级时只允许修改隔离区、适配器和必要的组合配置。

<a id="DR-010"></a>
### DR-010 配置按变化域归属

构建配置、板级资源配置、产品策略配置和运行时持久参数必须分域管理。配置的 owner、生成来源、默认值、校验和生效时机必须明确，不得用一个全局配置头承载所有变化。

<a id="DR-011"></a>
### DR-011 错误与可观测性跨层保留语义

边界必须定义稳定错误语义，并明确重试、降级、上报和恢复责任。适配器负责把底层错误映射为契约错误；不得静默吞错，也不得把供应商错误码直接泄漏到高层。

<a id="DR-012"></a>
### DR-012 新抽象必须通过准入问题

引入接口、工厂、注册表或事件总线前，至少回答：真实变化轴是什么、谁拥有选择权、是否存在第二实现或测试替身、增加了多少间接层、如何验证收益。回答不清时应保持直接设计并记录未来触发条件。

<a id="DR-013"></a>
### DR-013 语义、构建和运行视图必须一致

架构声明中的组件必须在构建目标、include 可见性和 Composition Root 中有对应关系；尚未实现的目录或模块必须显式标记为 planned，不得计入已落地能力。构建中存在但架构声明缺失的组件同样属于漂移。

<a id="DR-014"></a>
### DR-014 模块按语义角色而非目录名判层

每个项目模块必须声明稳定语义角色和主要变化原因。依赖检查依据角色执行，不得因路径名为 `Core`、`Device`、`BSP`、`Platform` 或 `Middleware` 就自动允许或禁止依赖；同一目录中不同角色的模块也必须分别判定。

<a id="DR-015"></a>
### DR-015 外部器件协议与 MCU/板级绑定分离

外部器件的寄存器、命令和状态逻辑必须依赖总线、IRQ、时间等稳定能力契约；具体 MCU 句柄、总线实例、地址、片选、引脚和供电绑定只允许存在于 MCU 机制、板级绑定或组合配置。固定且无复用价值的小实现可以物理合并，但公共契约不得泄漏环境类型。

<a id="DR-016"></a>
### DR-016 占位与弱实现必须可区分

`__WEAK` 默认实现、空实现、Null Object 和 planned 占位可以用于分阶段接线，但必须能被机器区分并计入未落地清单。缺失真实实现时不得静默进入死循环或静默返回成功，也不得在完成度统计中计为已实现。

## 架构门禁

<a id="GATE-001"></a>
### GATE-001 依赖方向检查

由 include/layer lint 或编译目标关系检查禁止依赖和组件环；新增违规必须使 CI 失败。

<a id="GATE-002"></a>
### GATE-002 公共头文件纯度检查

扫描 public 头文件中的环境特有类型和禁止 include，并对每个 Port 做独立编译检查。

<a id="GATE-003"></a>
### GATE-003 组件可见性检查

构建系统只暴露声明过的 public include 和显式链接依赖；用组件图检查越层依赖与循环依赖。全局 include 搜索路径数量应有上限并纳入趋势观察。

<a id="GATE-004"></a>
### GATE-004 替身与主机测试

关键策略至少能通过 Fake/Stub 在主机侧验证正常、超时、错误和恢复路径；测试不得依赖目标板全局初始化才能构造被测对象。

<a id="GATE-005"></a>
### GATE-005 资源与时序预算检查

对任务栈、静态内存、队列深度、ISR 时长、周期抖动和最坏执行时间建立预算及测量证据。超预算必须阻断发布或有正式豁免。

<a id="GATE-006"></a>
### GATE-006 发布与升级检查

供应商库、生成代码、板级配置或接口契约变更时，必须执行受影响构建、静态检查、目标板回归和接口兼容性检查。

<a id="GATE-007"></a>
### GATE-007 文档架构检查

文档清单、职责所有权、依赖无环、链接与声明依赖一致、锚点有效、规则 ID 唯一归属和引用完整性必须由仓库内脚本校验。

<a id="GATE-008"></a>
### GATE-008 三视图一致性检查

将架构组件清单与构建目标/源文件清单、public/private include 关系及 Composition Root 实例图进行比较；未接线、未声明或越权可见的差异必须失败或具有正式例外。

<a id="GATE-009"></a>
### GATE-009 语义层级映射检查

维护“实际路径/构建目标 -> 语义角色 -> 允许依赖角色”的机器可读映射。依赖扫描必须按角色而非厂商目录名报告违规文件、来源角色和目标角色，并对未分类模块返回失败。

<a id="GATE-010"></a>
### GATE-010 量产与升级门禁

镜像校验、版本与构建标识、Bootloader/App 边界、断电恢复、回滚、防降级、参数与校准区保护以及产线追溯必须有可复现的验证步骤，缺失时阻断发布打包或产线包生成。

## 机器化要求

凡是能被仓库结构、依赖图、构建脚本、静态扫描或测试稳定判断的约束，不能只写在设计文档中。提出新边界或发布规则时，必须同步给出：

1. 可机器检查的判定条件；
2. 推荐命令或 hook 入口；
3. 阻塞阶段：本地提交、CI 合并、发布打包或产线烧录；
4. 暂不能机器化的原因和人工确认方式。

规则实现必须输出违规文件、违规边界、修复方向和非零退出码。无法稳定自动判断的内容才保留为人工架构审查项。
