# 嵌入式架构设计方法

本文件只定义可重复执行的分析、设计和迁移方法。为什么做由[架构原则](architecture_principles_zh.md)解释，必须满足什么由[依赖规则与门禁](dependency_rules_and_gates_zh.md)定义，层级归一使用[语义层级模型](semantic_layer_model_zh.md)，可复用结构的名称与代价由[模式目录](architecture_patterns_zh.md)定义。

## 方法与模式的区别

方法是“按什么步骤工作并产生什么证据”，模式是“针对重复问题采用什么结构”。例如先用变化轴分析定位环境依赖，再决定是否采用 Ports and Adapters；不能因为知道模式名称就跳过分析。

<a id="AM-001"></a>
### AM-001 变化轴分析

1. 收集过去和可预见的变化：芯片、板卡、设备、协议、算法、产品配置、OS、工具链。
2. 为每类变化记录触发者、频率、当前触达文件和验证成本。
3. 将高频且扩散大的变化放到边界候选区。
4. 用简短说明或必要的变化矩阵解释边界理由；图和表用于帮助判断，不是额外交付要求。

验收证据：任一高概率变化都能指出预期 owner 和受控影响面。

<a id="AM-002"></a>
### AM-002 职责—非职责—所有权三联表

对本次涉及的模块说明职责、非职责和状态/资源 owner；已有代码或记录清楚时直接引用。若职责重叠或资源出现多个 owner，先理解协作关系，再判断是否需要调整边界或 API。

判断依据：关键行为和可变资源能够找到明确归属，不要求为每次任务另建模块表。

<a id="AM-003"></a>
### AM-003 契约先行设计

从调用者用例推导最小语义接口、稳定值对象、错误和执行上下文，优先复用现有公共 API。需要隔离环境或验证不确定性时，再选择适配器、测试替身或其他最小手段，不预设 Fake 与真实实现的固定先后顺序。

判断依据：调用者不需掌握无关实现细节，接口足以表达当前用例。是否使用替身取决于实际验证收益，不为匹配固定分层增加接口。

<a id="AM-004"></a>
### AM-004 架构先行脚手架

在深入业务实现前，围绕当前最小纵向切片建立可构建、可检查的骨架；已有结构满足要求时直接复用，不为未来功能铺空目录或空接口。用户只授权分析时，先给出组件、契约、接线和验收方案，不创建或修改骨架。

1. 明确本切片的组件职责、public/private 边界、依赖方向和组合位置，让实际源码与构建接线一致；已有记录足够时直接复用。
2. 按调用者用例定义最小契约，说明影响正确使用的输入输出、错误、生命周期、所有权和执行条件，不机械补齐无关字段。
3. 仅在隔离外部依赖、验证契约或分阶段接线确有需要时添加 Stub/Fake/Mock。标记 planned 与 implemented；缺失真实实现必须以明确的未实现错误、诊断或受控禁用路径暴露，不得静默成功。替身不得进入生产组合；不为满足数量要求制造第二实现或多余 Port。
4. 接通当前目标的编译、链接和组合入口；需要独立运行时再建立 harness 或 smoke 路径。选择公共接口、依赖方向、正常路径及关键错误中受本次影响的部分验证，复用已有入口。
5. 涉及固件目标时，按本次影响检查链接段与内存映射、启动路径/向量表、ISR 约束和硬件绑定；未触及的部分不扩展验证范围。骨架可验证后再补全业务逻辑，并接通真实实现。

验收证据：受影响的构建和接线可验证，选用的检查结果可复现，planned/弱实现未计入已完成功能。编译、替身行为与真实硬件行为分别说明，不要求所有骨架任务同时具备 harness、Fake 和目标板测量。

<a id="AM-005"></a>
### AM-005 最小纵向切片

选择一个真实变化点，沿一个用例贯通职责、必要接口、现有实现与接线，并选择能检验边界收益的回归。普通函数、静态绑定、适配器或替身按需要采用；切片结果用于修正下一步判断，不机械复制结构。

判断依据：本次变化被限制在预期范围，行为与关键失败路径有相称证据；需要隔离测试时，其构造不依赖无关环境初始化。

<a id="AM-006"></a>
### AM-006 架构适应度函数

把已明确且可稳定判断的关键约束接入现有检查，如禁止 include、公共类型、组件环或资源预算。选择本项目需要持续控制的指标，不为一次概念讨论新增检查器或门禁流程；历史债务按项目目标逐步收敛。

验收证据：已采用的检查能复现对应问题，需阻塞时返回非零；未接入 CI 或尚需人工判断的范围如实说明。

<a id="AM-007"></a>
### AM-007 绞杀式迁移

围绕一个调用链建立或复用合适的公共接口，逐步迁移到目标边界，必要时用适配器保持旧路径可回退。直到旧入口无使用者后再移除，不以一次性大重写作为解耦前提。

验收证据：每个迁移切片可独立构建、验证和回滚，旧/新路径的退出条件明确。

<a id="AM-008"></a>
### AM-008 证据分级评审

将结论分为已验证事实、有根据推断和未验证假设。目录名称只能证明设计意图；编译成功只能证明所纳入目标的代码可构建；硬件时序、并发和故障恢复必须由对应测量证明。

验收证据：每个完成声明都有同层级的命令、日志、静态报告或硬件记录，未验证项单独列出。

<a id="AM-009"></a>
### AM-009 SDK 命名语义归一

1. 收集实际目录、构建分组、公共头和初始化入口。
2. 暂时隐藏 `Core/Device/Driver/BSP/HAL/Platform/Wrapper` 等名称，只读取职责和依赖证据。
3. 按职责识别角色；需要正式依赖审计或工具输入时，再用角色 ID 记录模块映射。
4. 对外部器件继续拆出协议、传输能力、板级绑定和 MCU/OS 实现。
5. 基于实际职责与接口判断依赖，不基于字符串路径猜测层级；已有映射直接复用。
6. 涉及 APP 时，分别定位业务入口、任务/ISR 外壳和组合代码；按 DR-017 核对依赖与状态所有权，参考 GATE-011 选择相关验证。换芯片/板卡/OS 且业务契约不变时，APP 策略与领域逻辑不应跟随修改；若变化会改变采样能力或时序契约，先说明影响，不能保证所有平台迁移都无业务改动。

验收证据：更换另一厂商 SDK 的目录命名后，角色图和上层依赖规则无需重写，只需更新映射表。

<a id="AM-010"></a>
### AM-010 泄漏基线测量

需要比较存量泄漏或持续控制变化时，选择相关指标建立可重复基线，例如：

```text
按语义角色统计公共头中的环境类型出现次数
按语义角色统计直接 include 厂商/RTOS 头的文件数
统计全局 include 搜索路径条数
统计同一能力出现在几个不同目录
统计 planned/弱实现占位数量
```

按项目目标决定是否持续输出这些指标，检查接入参考 [AM-006](#AM-006)。局部边界分析可以直接使用相关调用和类型证据，不先做全库统计。

验收证据：基线命令、数值、快照提交号可复现，两次执行差异可解释。

<a id="AM-011"></a>
### AM-011 环境边界分析先行

自动检查依赖对来源、角色和环境类型的判断。先由模型读取代码与构建证据，优先复用已有项目规则；不能让脚本用目录名称猜测职责。

1. 读取本次相关构建配置与目录，区分**自维护代码**与**厂商/生成代码**，依据是来源与可改写性，不是路径名。
2. 找出直接接触环境的文件：include 了厂商 SDK、HAL、寄存器定义或 RTOS 头的，就是环境接触面。
3. 检查相关公共头的环境依赖：传递包含链是否触达环境头、公共 API 是否出现调用者不需要的环境类型。
4. 对涉及的模块说明职责判断，并附必要证据（公共类型、依赖方向或资源所有权）。
5. 仅在使用分层检查器或建立正式门禁时，按工具契约维护机器可读映射与确认依据。缺少确认不阻止继续分析、解释与已授权设计。

判断依据：职责与依赖结论能够由源码、类型和构建事实复核；作为工具输入的映射另需满足其必填字段。

反例：先假定"某目录名 = 某层"，再让工具按这个假定扫描。工具会忠实地按错误前提给出干净结果，该失效模式记为 SIG-010。

<a id="AM-012"></a>
### AM-012 对象、数据与生命周期建模

从用例中的名词、事件、变化原因和资源 owner 识别对象，再设计表示；不能先把全局变量装进结构体，再把它称为对象模型。

对象职责、身份、协作与生命周期按需结合 `aicoding-object-model-design`；内部字段、`cfg/ctx/data/ops`、类型、存储与有效期按需结合 `aicoding-data-model-design`。已有上下文足够时直接完成当前问题，不必串联入口。主架构不重复维护细节，仍按 DR-018 核对跨模块状态/资源归属与契约一致性。

验收证据：对象职责、操作、不变量与调用上下文清楚；验证与实际风险相称，不把结构体或函数表的存在计为设计完成。

<a id="AM-013"></a>
### AM-013 工程开发与 App 资产沉淀

**App 层的资产沉淀是工程开发必须考虑的事项。** 既包括可复用代码，也包括产品流程、状态机、业务规则、数据模型、异常处理与架构经验；适用范围可以是同一产品族。

1. 开始前先查已有成果，识别本次可以复用和积累的能力。
2. 实现中保持职责、接口与状态归属清楚，隔离芯片/板卡/OS 等偶然细节；有价值的缺陷场景保留为回归输入。
3. 收尾时提炼 App 及其他有价值成果，保留最小用法、验证入口和必要限制。服务、算法、协议、测试工具、数据样本与平台适配也可沉淀；数据保留其单位、采集条件和适用范围。
4. 后续接入时复用并反馈改进，保持清楚的维护来源，避免无必要的复制分叉。

输出简要说明沉淀了什么、放在哪里、后续怎样使用和验证即可。复用已有模块、测试和项目记录，不强制新建共享库、资产台账、等级或第二个项目；具体提取范围由真实需求决定。只分析时给出建议，不执行迁移。

## 按任务选择方法

```text
新项目可结合：AM-001、AM-002、AM-003、AM-004
存量调整可结合：AM-011、AM-009、AM-005、AM-007
需要趋势或持续检查时：AM-010、AM-006
报告结论时参考：AM-008
```

这些方法是思考工具，可按真实问题组合或跳过；不预设固定顺序、模式或额外交付物。选择仍需解释变化轴、收益和成本。

对象/数据变化时插入 AM-012；工程开始与收尾按 AM-013 考虑 App 及其他资产沉淀。只分析时输出相应设计与资产建议，不执行提取或迁移。
