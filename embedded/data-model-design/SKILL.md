# 数据模型设计

默认简体中文。回答“字段为什么存在、由谁维护、谁能读取、何时有效”，从业务数据流、变化和目标约束推导具体表示。

## Skill 类型

属于 `reusable-domain-knowledge` 与 `team-expertise`：沉淀数据语义与表示选择的判断方法。

## 字段先按语义归属

| 概念 | 主要内容 | 设计重点 |
|---|---|---|
| `cfg` | 资源绑定、参数、选项、限值与策略配置 | 来源、校验、生效时机、是否可变及能否共享 |
| `ctx` | 每实例私有工作状态、在途操作、计时和必要依赖 | 唯一写入方、初始化/复位、并发及寿命 |
| `data` | 业务输入/结果、当前值或对外快照 | 单位、范围、时间/序号、质量与读写权限 |
| `ops` | 对象提供的类型化行为契约 | 参数、返回/错误、阻塞、完成与副作用 |

这组词帮助区分语义；项目可以采用其他名称、内嵌或指针、一个或多个结构体。保持可理解的类型、权限与寿命，不因追求统一抹去真实差异。

## 设计时怎样思考

围绕当前结构体、调用链和业务数据流，选择会改变方案的问题思考，不逐项套模板：

- 这个字段为什么存在？它描述参数、工作过程、目标、反馈还是派生结果，和哪些内容一起变化？
- 谁产生并维护它，谁需要读取，什么时间有效？生命周期状态、设备就绪与业务状态是不同含义还是无谓重复？
- 分开或合并有什么收益？大小、共享、寿命、并发与目标约束如何影响内嵌/指针、只读/可变和存储选择？
- 调用者需要采集能力还是已有结果？失败、过期和部分更新怎样表达，什么边界足以隔离真实变化？
- 现有表示是否已经够用？用哪项最小验证能消除关键不确定性，哪些单位/类型检查可交给已有工具？

比较与当前用例有关的选择及代价，再确定最小表示；无必要拆分时保留现状。

## 按需深入与协作

具体字段分类、内嵌/指针、共享与只读性、采样快照、ops 互换及教材示例取舍，读取[字段归属与强类型组合](references/field_design_zh.md)。

若问题需要重新确定对象身份、协作或生命周期，可结合 `aicoding-object-model-design`；涉及系统模块职责或依赖变化时，可结合 `aicoding-architecture`。按实际缺口协作，已有上下文足以完成问题时直接处理，不将三个 Skill 必选串联或来回转交。C 实现结合项目规范及 `aicoding-c99-standard-c`。

## 验证与输出

输出字段职责与数据流、类型/存储和访问选择、理由及必要验证。已确定的类型、签名和换算问题交给已有工具或测试；业务语义与取舍结合实际需求，硬件与并发结论保留验证范围。

**必须考虑 App 层资产沉淀**：哪些业务数据模型、单位与有效性契约、参数语义和异常样本值得保留复用。沿用已有代码、测试和简短说明承载即可。
