## 适用范围与文件归属

先将文件判定为项目自研、自动生成或第三方代码。

判断证据包括：

- 文件头的生成标记、许可证和版权所有者；
- STM32Cube、SysConfig、配置器或 IDL 的输入和再生脚本；
- 包管理、submodule、vendor 目录和上游仓库；
- 当前团队是否拥有接口和实现的维护责任。

自动生成和第三方代码默认保持实际编码和局部风格，只做必要逻辑修改。新项目和项目自研代码对新增或修改函数执行本参考的固定规则。

## 命名与格式

| 对象 | 规则 | 示例 |
|---|---|---|
| 文件 | `snake_case` | `motor_control.c` |
| 函数 | `snake_case` | `motor_control_init` |
| 局部变量、参数 | `lowerCamelCase` | `targetSpeed` |
| 文件级或全局可变状态 | `g_` + `lowerCamelCase` | `g_motorState` |
| 宏、枚举值、标签 | `UPPER_SNAKE_CASE` | `MOTOR_STATE_RUN` |
| `typedef` 抽象类型 | `PascalCase` | `MotorConfig` |

- 使用 4 个空格缩进，禁止 TAB；
- 行宽默认不超过 120 列；
- 一行只写一条语句；
- 函数左大括号独占一行；
- 控制语句左大括号放在语句行末；
- 所有控制语句必须使用大括号；
- 枚举定义中的每个枚举值必须逐项注释其具体含义；
- `case/default` 缩进一级并明确 `break`、`return`；仅在有意 fallthrough 时允许省略退出语句，并在相邻 `case` 之间注明目标和原因；
- 优先使用函数或 `static inline`，避免具有副作用的函数式宏。

完整布局见[示例实现](../assets/cursor_example.c)及[格式配置](../assets/clang-format.yaml)。

## 函数命名、入参与设计

本节只约束项目自研的新函数和任务确实需要修改的函数。稳定公共 API、标准规定符号、自动生成代码和第三方接口保持原名；需要迁移时单独评估调用链、ABI 和回归成本。

### 功能分解与接口定版

先定义功能需要的数据，再设计函数接口。不要从现有大结构体中随意取用字段，再反过来解释函数职责。由 Agent 查找已有实现、推导方案并完成设计判断；只把会改变方案且无法从现有上下文确定的契约交给用户决定。

#### 设计审阅稿

审阅稿复用任务回复、项目已有设计说明和公共头文件草案，不要求新增独立计划文档或重复维护一份函数清单：

- 功能流程及模块关系，包括正常处理、失败处理、数据流和执行上下文；
- 本次新增、修改的函数，以及直接复用的接口入口；稳定库只列接入入口与依赖契约，不展开无关私有实现；
- 每个函数的名称、职责、调用关系和可见性；
- 公共接口声明，以及输入输出、状态和副作用契约。

已定版且未变化的接口直接沿用。新增功能、新模块或跨边界变化先形成可审查的设计，再在用户授权范围内实现。明确的实现请求构成该范围授权；只有用户要求先审方案，或存在影响行为但尚未确定的选择时，才等待决定，不重复审批已有合同。

公共接口至少说明：

| 内容 | 需要明确的问题 |
|---|---|
| 输入 | 类型、含义、单位、范围、有效性；有时序要求时说明数据对应的时刻 |
| 输出 | 结果含义、单位、有效条件；返回值与输出参数分别表示什么 |
| 失败 | 错误如何报告，输出和内部状态如何处理，调用方应采取什么动作 |
| 状态 | 谁拥有、谁修改；配置初始化、运行状态复位和参数更新如何区分 |
| 使用约束 | 指针生命周期、是否保留指针、可重入性、阻塞性、调用顺序及必要的硬件副作用 |

传入上下文结构体时，也必须说明读取哪些数据、允许修改哪些状态。仅把参数替换为一个 `context` 指针，不能证明依赖已经清晰。

公共函数签名不变，但单位、有效范围、时序、失败语义或调用约束改变，仍属于公共契约变化，需审查受影响调用者并确认处于任务范围。保持既定合同的私有函数新增、拆分、重命名或参数调整可以直接完成，并在交付时说明实际调整。

#### 函数可见性与文件边界

| 使用范围 | 组织方式 |
|---|---|
| 模块外需要调用 | 在公共 `.h` 中声明稳定接口 |
| 仅同一 `.c` 内使用 | 声明为 `static`，不进入公共头文件 |
| 模块内部跨 `.c` 使用 | 确有需要时使用内部头文件，并限制其构建可见范围 |

文件边界由职责决定，不把流程中的每一步机械拆成一对 `.c/.h`。内部头文件本身不能保证隔离，仍须检查公共 include 路径、调用方和实际构建依赖。稳定公共 API、生成代码和第三方文件继续遵守原有兼容性与归属边界。

#### 降低数据与执行耦合

- 一个函数完成一个完整、可解释的行为，不为行数指标制造无意义的转发函数；
- 结构体只聚合语义相关的数据，不把整个产品对象传给只需要少数字段的算法，也不为减少参数数量而创建“大参数包”；
- 可独立计算的逻辑与硬件访问、调度分开；驱动和状态机保留真实需要的状态与副作用，并通过明确接口表达；
- 仅有真实状态或资源生命周期时才提供 `init/reset/deinit`，不为纯计算功能机械增加生命周期接口；
- 可变状态有明确所有者和写入者；需要多实例时使用独立实例状态，不用隐藏的全局变量或静态局部变量串联不同实例；
- 公共头文件不引入无关的产品对象、厂商寄存器或 RTOS 类型；分层沿用 Architecture 的 `DR-001/003/007/008/012`，不另建一套层级；
- 参数检查责任必须明确，避免漏检及无意义的逐层重复检查；不能因为历史规范默认由调用者负责，就取消不可信公共入口的必要检查；
- 失败路径遵守已约定的输出有效性和状态处理方式，不让调用方把上次结果误认为本次有效输出。

#### SVPWM 边界示例

先查找已有调制能力。可复用的正式控制资产示例为 `foc_svpwm.c/.h`；实际接入先确认资产可访问及契约匹配，匹配时复用现有实现和 API，不为展示新目录而复制另一份算法。

| 项目 | 设计说明 |
|---|---|
| 复用入口 | `foc_svpwm_init(FocSvpwm *controller)` 与 `foc_svpwm(FocSvpwm *controller)`，保留现有接口 |
| 核心输入 | `controller.config` 与 `controller.input`：约定归一化基准的 αβ 调制量和调制配置 |
| 核心输出 | `controller.state`：三相占空比、缩放系数、限幅及有效状态 |
| 核心职责 | 完成调制计算；初始化接口仅按现有实现建立实例初值 |
| 外部职责 | ADC 采集、输入准备、PWM 寄存器提交和保护动作 |
| 解耦要求 | 不传入整个 `MotorCtrl`，不在调制计算中读取 ADC 或写 PWM 寄存器 |

此例说明功能与接口边界，不改变已有调制算法、归一化尺度、调度、错误策略或接口命名。目标工程已有其他经过验证的实现时，优先核对并适配该实现。

#### 验证边界

职责、内聚性和副作用语义属于设计审查；公共头文件自包含、编译、依赖约束和行为结果使用已有工具验证。没有对应的可靠检查器或架构映射时，明确记录人工审查项或待验证项，不宣称普通 lint 能自动证明“低耦合”。

头文件依赖、单一职责、共享状态、参数检查、失败语义、内聚数据与接口说明分别选择适用的设计方法和证据；规则目录中的覆盖标记不代表本次候选代码已经通过检查。

已确认的接口和有效授权继续复用。不得在发布时为了暴露符号去掉 `static`，也不要求所有返回指针都指向静态局部变量；按实际可见性、所有权与寿命设计。行数、参数数和扇出阈值是设计审查信号，不机械制造文件、结构体或抽象层。

### 函数命名

#### 清晰性与动作结构

函数名必须清晰、明确，并以函数要执行的动作命名。移除可选模块前缀后，核心动作短语采用动词或“动词 + 名词”结构；不要为节约字符使用模糊字符，也不要把名称写成英语长句或内部实现步骤。

公共函数默认采用 `<module>_<verb>[_<object>]`，文件私有 `static` 函数可采用 `<verb>[_<object>]`。同一产品或项目保持统一命名风格；本规范对项目自研新函数统一采用 `snake_case`。

#### 缩写规则

- 除常见通用缩写外使用完整英文单词，不得使用汉语拼音；
- 较短的单词可以通过去掉元音形成缩写，较长的单词可以取开头若干字母；已有公认缩写时优先使用公认形式；
- 同一完整单词在同一项目中只使用一种缩写，不得临时发明近义写法；
- 协议词汇的缩写与协议保持一致，标识符大小写再按项目命名风格转换；
- 系统专用缩写必须在项目命名表、模块文档或相邻注释中统一说明；
- 稳定公共 API 不为套用新缩写表而批量重命名，迁移时单独评估兼容性。

统一缩写表：

| 完整单词 | 缩写 | 完整单词 | 缩写 |
|---|---|---|---|
| `argument` | `arg` | `buffer` | `buff` |
| `clock` | `clk` | `command` | `cmd` |
| `compare` | `cmp` | `configuration` | `cfg` |
| `device` | `dev` | `error` | `err` |
| `hexadecimal` | `hex` | `increment` | `inc` |
| `initialize` | `init` | `maximum` | `max` |
| `message` | `msg` | `minimum` | `min` |
| `parameter` | `para` | `previous` | `prev` |
| `register` | `reg` | `semaphore` | `sem` |
| `statistic` | `stat` | `synchronize` | `sync` |
| `temp` | `tmp` |  |  |

本表是项目自研新代码的统一基线；稳定公共 API 按兼容性边界单独处理。

#### 项目命名结构与长度

新函数名同时满足：

- 使用 `snake_case`；
- 不超过 32 个字符；
- 默认不超过两个下划线，即最多三个下划线分隔词；
- 每个下划线分隔词不超过 12 个字符；
- 公共函数默认表达“模块 + 动作 + 可选对象”，文件私有 `static` 函数可省略模块前缀；
- 多词模块需要同时表达动作和对象时，使用项目统一登记的单词前缀。缩写必须稳定、无歧义且可搜索，不得由每个函数临时发明。

| 意图 | 推荐 | 禁止或需要整改 |
|---|---|---|
| 多词模块设置目标 | `mc_set_target` | `motor_control_set_target` |
| FoE 读取块 | `foe_read_block` | `retrieve_current_foe_block` |
| 检查 manifest | `manifest_check` | `manifest_finalize` |
| 布尔状态查询 | `axis_is_ready` | `axis_ready_status_check` |
| 文件私有解析 | `parse_header` | `handle` |

`motor_control` 缩写为 `mc` 只是示例；实际前缀必须来自项目命名表、现有模块公共前缀或用户确认。同一前缀不得同时表示不同模块。

#### 动作词语义

| 动作 | 语义 |
|---|---|
| `init` / `deinit` | 建立或释放模块运行条件，不隐含启动业务动作 |
| `get` | 取得模块已有或缓存值，不主动访问外部数据源 |
| `read` | 主动读取硬件、存储、通信或其他数据源 |
| `peek` | 查看队列或流中的数据但不消费 |
| `set` | 设置模块属性或期望值 |
| `write` | 写入硬件、存储、通信或其他外部目标 |
| `update` | 根据当前输入推进、刷新或重算已有状态 |
| `is` / `has` / `can` | 返回单一布尔判断，不编码错误原因 |
| `check` | 执行合法性、完整性或状态检查，并返回布尔值或统一检查结果 |

优先使用 `init/cfg/get/set/read/write/check/clear/reset/start/stop/open/close/update/send/recv/parse/create/delete/save/load` 等常用动作。新函数名不得使用 `finalize`、`commit`、`retrieve`、`instantiate`；分别选用语义更明确的 `end/close`、`save/write/apply`、`get/read`、`create/init`。`manifest` 是 OTA、Bootloader 等领域中的正式名词，可以在 `manifest_check` 等名称中使用。

`process/handle/control/service/manager` 不得脱离明确模块或对象单独充当动作。若 `foe_process` 这类名称仍是项目内最准确的状态机入口，可以保留；不得用模糊词掩盖多个职责。

#### 反义动作与函数指针

互斥或相反动作使用统一的反义词组：

| 动作 | 反向动作 | 动作 | 反向动作 |
|---|---|---|---|
| `add` | `remove` | `begin` | `end` |
| `create` | `destroy` | `insert` | `delete` |
| `first` | `last` | `get` | `release` |
| `increment` | `decrement` | `put` | `get` |
| `add` | `delete` | `lock` | `unlock` |
| `open` | `close` | `min` | `max` |
| `old` | `new` | `start` | `stop` |
| `next` | `previous` | `source` | `target` |
| `show` | `hide` | `send` | `receive` |
| `source` | `destination` | `copy` | `paste` |
| `up` | `down` |  |  |

项目采用 `recv` 作为 `receive` 的缩写时，在同一接口族中保持一致。函数指针除项目统一前缀或后缀外，动作和对象部分遵循函数命名规则；函数指针 `typedef` 作为类型时仍按类型命名规则使用 `PascalCase`。

### 函数入参

参数顺序默认采用：

1. 实例或上下文指针；
2. 完成动作所需的输入；
3. 输出参数。

缓冲区与其长度或容量视为一个参数组，必须相邻，并按缓冲区的输入/输出方向放置。参数和局部变量使用 `lowerCamelCase`。

```c
ResultCode foe_read_block(FoeContext *context,
                          uint32_t blockIndex,
                          uint8_t *buffer,
                          size_t bufferSize,
                          size_t *readLength);
```

该接口中 `buffer`、`bufferSize` 和 `readLength` 构成输出缓冲区组；只有返回 `RESULT_OK` 后，`buffer[0..*readLength)` 和 `*readLength` 才有效。

入参契约：

- 不修改调用者数据的指针使用 `const`；零参数函数显式写 `(void)`；
- 数组、缓冲区和字符串携带 `size_t` 长度或容量，不依赖哨兵或隐藏常量；
- 时间、频率、地址等单位无法由类型确定时写入参数名，例如 `timeoutMs`、`frequencyHz`；
- 小型标量按值传递，状态、较大对象和多实例模块通过明确上下文指针传递；
- 注释明确指针是否可空、由谁拥有、有效期、函数是否保留该指针以及调用期间是否允许别名；
- 输出参数位于输入之后，明确各返回条件下的有效性；默认检查完成后再提交，已有清空或部分成功合同需准确说明，不能暴露未约定的半更新结果；
- 避免含义不明的布尔开关，使用枚举表达模式、策略或方向。

参数超过 5 个时触发接口设计审查，但不自动判错，也不强制改成结构体。审查以下问题：

- 函数是否混合了两个动作；
- 是否存在可从上下文或其他参数可靠推导的冗余值；
- 多个布尔开关是否应改为枚举；
- 多个参数是否确实具有共同语义、生命周期和校验规则；
- 参数组是否会由多个接口复用并作为一个稳定概念演进。

只有最后两项成立时才定义配置、请求或描述结构体。不得创建只为降低表面参数数量、混入无关输入和输出的参数包。

### 函数职责与返回值

- 一个函数只承担一个可观察职责和一个主要变化原因；名称、输入、输出和副作用共同表达该职责。
- 校验、纯计算、硬件 I/O、状态迁移和调度在具有独立语义或测试边界时拆分；简单的必要前置校验可以保留在被调用接口内。
- 无失败语义的纯查询可直接返回值；可能失败的函数返回模块统一的错误枚举，并通过输出参数返回计算结果。
- `bool` 只表示真正的真假问题，不能让 `false` 同时表示“状态为假”和“调用失败”。
- 优先通过参数和返回值传递数据，避免读取或修改隐藏全局状态；不可避免的共享状态必须说明所有者和同步策略。
- 明确函数是否阻塞、是否可重入、允许的 ISR/任务上下文、共享状态保护和硬件副作用。

以下指标是设计审查信号，不是机械拆分条件：

| 信号 | 审查动作 |
|---|---|
| 超过 50 行非空非注释代码 | 检查是否混合职责或缺少可测试边界 |
| 嵌套超过 4 层 | 优先使用守卫条件、提前返回或状态拆分 |
| 参数超过 5 个 | 执行参数内聚性审查 |
| 非调度函数直接调用超过 5 个函数 | 检查是否承担了过多编排职责 |

不得为了满足数字指标生成只转发一次、没有独立语义和测试价值的碎片函数。

### 回调函数

设计回调前必须回答：谁调用、何时调用、运行于 ISR/任务/主循环中的哪一个上下文、是否允许阻塞，以及注册对象能存活多久。

通用回调默认使用“上下文指针 + 类型化事件 + 可选只读事件数据”：

```c
typedef void (*I2cCallback)(void *callbackContext,
                            I2cEvent event,
                            const I2cEventData *eventData);

ResultCode i2c_set_callback(I2cContext *context,
                            I2cCallback callback,
                            void *callbackContext);
```

- 不需要事件数据时省略 `eventData`，不得添加永远无效的占位参数；
- `callbackContext` 由注册者提供，回调内只做一次明确的类型转换，不依赖临时栈对象或隐藏全局变量；
- 模块实例和 `callbackContext` 的生命周期必须覆盖整个注册期，注销或销毁后不得再回调；
- `eventData` 默认只在本次回调期间有效，回调若需保留必须复制到自己拥有的存储；
- ISR 或调用上下文不确定的回调必须非阻塞，不动态分配、不等待锁、不执行复杂日志或协议处理；
- 多实例模块为每个注册实例保存独立的回调和上下文，不使用单一全局回调槽覆盖其他实例。

### 门禁边界

函数名长度、下划线数量、单词长度和原型参数数量可以作为后续 parser/lint 候选。本次规范不要求新增低可靠性的正则脚本；动作是否准确、缩写是否清晰、是否属于汉语拼音、协议或系统专用缩写是否一致，以及参数内聚性、单一职责、回调调用环境和生命周期，继续由人工审查。

项目编译器支持时，启用 `-Wimplicit-fallthrough` 或等效告警检测未标记贯穿；枚举值注释的语义准确性、贯穿必要性和注释目标/原因继续由人工审查。不得用只统计注释数量的正则检查冒充语义门禁。

## 文件组织

新建或大幅重写项目自研 `.c` 文件时，优先采用：

1. 项目现有文件头；
2. `#include`；
3. 宏与常量；
4. 类型定义；
5. 文件级 `static` 状态；
6. 内部声明；
7. 内部 `static` 函数；
8. 对外函数。

不要写死年份、公司、作者或版权。新文件优先复用项目模板；没有模板时采用本 Skill 的结构与示例，按实际职责填写。缺模板本身不构成阻塞。

## 注释与修改记录

### 普通说明与分区标记

普通说明使用 `/* 注释内容 */`，默认写直白中文，末尾不加句号。注释位于对应代码右侧或紧邻上方，上方注释与前一段代码空一行，并和下方代码保持同级缩进。

```c
/* 统计任务的数量上限 */
#define MAX_ACT_TASK_NUMBER 1000U

#define CURRENT_SAMPLE_HZ 20000U /* 电流采样频率，单位Hz */
```

分区标题、重点代码段可以使用大块星号或星号分割线，不将它们与普通单行说明混用。分割线本身不能替代函数或参数的含义说明。

```c
/************************ 电流环计算 ************************/
/* 使用限幅后的总电压，避免积分继续向饱和方向增长 */
current_update();
```

默认不为普通说明添加Doxygen标记或格式标签。只有项目明确要求生成Doxygen文档时才使用相应格式；历史参考和旧模板不能覆盖用户当前要求。第三方、自动生成代码保持原有风格，不为统一注释而批量改写。

### 参数和结构体字段

先说明用途，再给单位和必要范围；用户设置与模块维护的运行数据要区分。容易误用的比例或尺度给一个填写例子，不用术语或变量名的中文翻译代替说明。

```c
typedef struct {
    double periodS;    /* 调用周期，单位s；20kHz填0.00005 */
    double amplitudeA; /* 电流变化峰值，单位A；填0.2表示最大变化0.2A */
    double riseRatio;  /* 上升段占周期的比例；填0.2表示用周期的前20%上升 */
} SignalConfig;
```

运行状态写清保存什么、何时更新、是否需要用户填写。例如“已经输出多少个点，由计算函数更新，用户不用赋值”。涉及多路或中断时说明具体访问方式，例如“两路分别使用两个变量，同一路不要同时在任务和中断中计算”。

### 枚举值

每个枚举值在右侧或紧邻上方说明具体含义。类型整体说明不能替代逐项解释，不只重复枚举名。

```c
typedef enum {
    MOTOR_STATE_IDLE = 0, /* 电机未使能，可以接收启动请求 */
    MOTOR_STATE_RUN,      /* 正在运行闭环控制 */
    MOTOR_STATE_FAULT     /* 已发生故障，禁止电机输出 */
} MotorState;
```

### `switch` 有意贯穿

`case`通常以`break`或`return`结束；有意继续执行下一`case`时，在两个`case`之间明确目标和原因，并与下一`case`同级缩进。

```c
switch (state) {
    case MOTOR_STATE_RETRY:
        motor_prepare_run();

    /* fall through：继续执行MOTOR_STATE_RUN，复用已准备好的运行处理 */
    case MOTOR_STATE_RUN:
        motor_update();
        break;

    default:
        motor_stop();
        break;
}
```

纯粹的分割星号不能作为贯穿说明。编译器需要的`fall through`标识可以保留，后面补中文的目标和原因。

### 函数头

简单私有函数用一句用途说明。公共接口按适用项写用途、输入、输出、返回和约束，说明失败行为、单位、寿命与调用上下文；不加每行星号或 Doxygen 标签。结构与省略条件见[统一注释体系](function-and-comment-style-zh.md)，完整合同见[示例头文件](../assets/cursor_example.h)。

### 函数内部

复杂逻辑说明关键步骤、计算依据、边界或硬件时序。简单函数若已能从名称和函数头看懂，不强制再放内部注释。禁止`i++; /* i加1 */`这类逐行翻译。

```c
/* 先检查命令，避免错误输入覆盖当前有效设置 */
if (command == NULL) {
    return RESULT_INVALID_ARGUMENT;
}
```

### 修改与问题追溯

默认通过Git提交、CHANGELOG或项目已有任务记录追溯作者、日期、原因。不要自动在每个函数前生成Modification History、Bug Fix和版本表。只有项目明确需要代码内记录时才按要求补充，并保持普通注释简洁，不虚构元数据。

代码内保留对维护有用的原因，例如“状态必须在写入完成后再发布，避免另一个执行者读到未完成的数据”。不要只写“原子发布”而不说明当前代码保证了什么。

## 安全性与可移植性

- 函数保持单一职责；50 行非空非注释代码和 4 层嵌套作为设计审查信号，不为满足指标机械拆分；
- 所有可能失败的 API 立即检查返回值；
- 对 API 参数、文件、报文、IPC 数据和跨信任边界的共享状态做显式校验；
- 不使用 `assert` 校验外部输入；
- 动态内存、锁、句柄、队列和信号量在所有退出路径正确释放；
- 复杂资源清理可使用单一 `cleanup:` 出口；
- 文件私有符号使用 `static`；共享状态说明互斥、原子或中断保护策略；
- 对象内的字节访问使用合适的字符类型并遵守对象边界；地址往返仅在实现提供且目标约定允许时使用 `uintptr_t`，不以整数运算绕过边界或对齐要求；
- 长度和索引使用 `size_t`，缩窄前检查边界；
- 生产代码使用项目日志接口，不遗留裸 `printf` 或敏感信息；
- 调试钩子和测试代码不得无保护地进入发布路径。

## 审查清单

- 是否先检查已有实现，并给出本次功能流程、模块/函数职责、可见性及公共接口契约；
- 设计与实现是否处于当前任务授权范围，是否处理了影响行为的未决选择，并复用已有确认；
- 是否正确判断项目自研、自动生成或第三方代码；
- 是否保持第三方和生成代码的实际编码及局部风格；
- 项目自研新增或修改函数是否满足命名、4 空格和大括号规则；
- 枚举定义是否逐项解释每个枚举值；注释是否位于代码右侧或紧邻上方，上方注释是否与前段代码空一行且同级缩进；
- 每个 `case` 是否明确结束；有意 fallthrough 注释是否位于相邻 `case` 之间并写明目标和原因；
- 新函数名是否不超过 32 个字符、默认不超过两个下划线、每个词不超过 12 个字符；模块短前缀是否统一且无歧义；
- 函数名是否采用动词或“动词 + 名词”的核心动作结构，是否避免英语长句和内部实现步骤；
- 是否只使用完整英文单词或统一缩写，未使用汉语拼音；协议和系统专用缩写是否有一致依据；
- 函数指针的动作和对象是否遵循函数命名规则，反向操作是否使用统一的反义词组；
- 动作词是否准确，是否误用禁用词或用模糊词掩盖多个职责；
- 参数是否按上下文、输入、输出排列，缓冲区与长度相邻，输入指针正确使用 `const`，单位和生命周期明确；
- 超过 5 个参数时是否完成接口审查，结构体是否确实代表稳定内聚的参数组；
- 返回值是否区分失败和业务布尔状态，各返回条件下的输出有效性是否符合真实合同；
- 函数职责、副作用、阻塞性、可重入性和调用上下文是否明确，复杂度指标是否作为审查信号而非机械拆分目标；
- 回调是否明确调用者、执行上下文、上下文对象和事件数据生命周期，并支持多实例和非阻塞约束；
- 函数是否有必要用途说明，复杂逻辑是否说明计算依据；简单函数没有内部注释不单独判错；
- 字段是否说明作用、单位/范围和必要例子，用户填写的数据与模块维护的状态是否区分；
- 普通注释是否使用简易格式，分区或重点星号是否有助于阅读；变更是否可从现有记录追溯；
- 是否覆盖或伪造版权、作者、年份；
- 返回值和外部输入是否校验；
- 是否存在宏副作用、指针截断或 `size_t` 未检查缩窄；
- 资源是否在所有退出路径释放；
- ISR、任务、DMA 和共享状态是否有同步说明；
- 是否产生与任务无关的格式化或重命名 diff。
