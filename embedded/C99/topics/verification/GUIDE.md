# 实际验证与门禁设计

## 触发语境

规范落地、限制生成、Hook、Lint、格式检查、配置 overlay、编译、测试、静态分析或声称“符合规范”时使用本页。
先确定实际候选和预期行为，再选择工具；不要把 Kit 默认示例的通过结果当成用户文件的证据。
本页由 C99 总入口按需加载，具体命令与事件合同只引用验证参考中的当前实现。

## 必要输入

- 实际项目根、候选文件、文件归属、编码/EOL、工作树或暂存区范围，以及本次 diff。
- 项目明确选择的格式与命名配置、overlay 顺序、工具版本和真实目标构建入口。
- 行为风险、已有回归用例、可用 host harness、硬件条件和必须保持的输出不变量。

## 选择相称证据

| 要回答的问题 | 优先证据 | 不能据此声称 |
|---|---|---|
| 命名、布局是否符合配置 | 实际候选上的格式与配置驱动 Lint | 输入输出语义正确 |
| 声明、链接和目标特性是否可用 | 真实工具链构建、独立头编译及必要的 map | 所有路径行为正确 |
| 边界和失败行为是否保持 | 能区分行为的测试与失败注入 | ISR 时序或硬件交互已通过 |
| 所有权、单位和上下文是否合理 | 接口合同与调用链人工复核 | 已自动完成全部语义证明 |
| 时序、DMA 或设备效果是否成立 | 条件明确的目标板测量与记录 | 其他负载、板型或版本同样通过 |

## 执行方法

1. 先复用项目已有的编译器、测试、格式器与 C Kit；不要在 Skill 或 Hook 中再造一套 C 检查器。
2. 显式选择候选与配置，确认 overlay 最终值；新通用命名不能覆盖已有有效项目约定。
3. 区分 `check` 的格式覆盖与 `verify` 的候选验证路径，记录实际执行的工具及退出状态。
4. 检查暂存区时使用真实 index 内容或经验证的快照，不能只列暂存文件名后读取较新的工作树。
5. 使用已有相称测试验证变化；只改可逆的格式或注释时不机械新增行为测试。
6. 把诊断对应到具体文件和约束；先修真正阻塞项，审查提示结合上下文判断并说明处理结果。
7. 按文件原编码与 EOL 写回；格式修复之前先确认工具能安全处理，必要时保留原始字节验证。
8. 交付实际命令、检查对象、配置、结果和未覆盖边界，避免用“全通过”隐藏检查范围。

## Hook 与配置边界

- Hook 负责在正确时机调用有界、只读的检查，并反馈可定位诊断；不自动重写、提交、推送或操作硬件。
- 项目显式开启规则后才阻塞；工具缺失、配置错误与代码违规分别报告，不静默退化成已验证。
- 普通中文注释字段检查只验证要求的字段和可识别参数是否出现，不能验证单位、可空性或失败语义。
- 长度、嵌套和参数数量是审查信号；通用 profile 的 50 行/4 层/5 参数使用 warning，旧 profile 依其配置。
- 文件归属与编码首先由真实项目确定；第三方、自动生成文件不因统一风格要求而批量改写。
- Hook 是辅助门禁，不能替代 Git 门禁、CI、代码审查或目标板验证；定义变更按产品信任流程复核。

## 实际验证与结束条件

至少在实际候选上执行本次风险需要的格式/Lint 和编译或测试，确认失败会正确阻塞、提示不会冒充错误。
修改检查器时使用少量能揭示误报、漏报和旧配置回归的正反例；只改指南则校验链接与入口契约。
工具通过后不无理由重复扩大测试；新改动、新失败或未解疑点才触发额外验证。
没有环境可执行时写清尚未验证的项目及可复现命令，不伪造输出，也不把人工阅读称为自动执行。
