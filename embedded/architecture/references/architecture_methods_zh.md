# 嵌入式架构设计方法

本文件只定义可重复执行的分析、设计和迁移方法。为什么做由[架构原则](architecture_principles_zh.md)解释，必须满足什么由[依赖规则与门禁](dependency_rules_and_gates_zh.md)定义，层级归一使用[语义层级模型](semantic_layer_model_zh.md)，可复用结构的名称与代价由[模式目录](architecture_patterns_zh.md)定义。

## 方法与模式的区别

方法是“按什么步骤工作并产生什么证据”，模式是“针对重复问题采用什么结构”。例如先用变化轴分析定位环境依赖，再决定是否采用 Ports and Adapters；不能因为知道模式名称就跳过分析。

<a id="AM-001"></a>
### AM-001 变化轴分析

1. 收集过去和可预见的变化：芯片、板卡、设备、协议、算法、产品配置、OS、工具链。
2. 为每类变化记录触发者、频率、当前触达文件和验证成本。
3. 将高频且扩散大的变化放到边界候选区。
4. 输出变化矩阵，而不是直接画分层图。

验收证据：任一高概率变化都能指出预期 owner 和受控影响面。

<a id="AM-002"></a>
### AM-002 职责—非职责—所有权三联表

为每个模块同时写出唯一职责、明确非职责，以及状态/资源 owner。若两个模块的职责句子高度相似，或一个资源出现多个 owner，先调整边界再设计 API。

验收证据：模块表中不存在空 owner、重复 owner 或无法归属的行为。

<a id="AM-003"></a>
### AM-003 契约先行设计

从调用者用例写出最小语义接口、稳定值对象、错误和执行上下文，再适配现有 HAL/RTOS/设备接口。先构造一个 Fake 验证契约是否足以驱动核心逻辑，最后编写真实 Adapter。

验收证据：核心测试只依赖契约和 Fake；公共接口不需要包含环境头文件。

<a id="AM-004"></a>
### AM-004 架构先行脚手架

在业务实现前建立组件清单、目录、public/private 边界、构建目标、Composition Root 占位和自动边界检查。每个占位组件标记为 planned 或 implemented，避免把空目录误报为已落地能力。

验收证据：语义目录、构建目标和架构清单可以逐项对应；空占位不会参与完成度统计。

<a id="AM-005"></a>
### AM-005 最小纵向切片

选择一个真实变化点，贯通一个用例、一个核心模块、一个 Port、一个真实 Adapter、一个 Fake、组合接线和相应门禁。切片完成后再复制结构到下一个热点。

验收证据：一次替换或故障注入只修改组合配置/实现侧，核心测试无需目标板初始化。

<a id="AM-006"></a>
### AM-006 架构适应度函数

把关键约束转换为持续执行的检查：禁止 include、public 头纯度、组件环、构建可见性、资源预算、三视图差异和文档拓扑。先对新增代码设零容忍，再逐步给历史债务设置基线下降目标。

验收证据：违规能由本地命令和 CI 稳定复现，并返回非零状态。

<a id="AM-007"></a>
### AM-007 绞杀式迁移

在旧接口外建立新 Port/Adapter，选择一个调用链迁移到新边界，保持旧实现可回退；逐步移动调用者，直到旧入口无使用者后再移除。不要以一次性大重写作为解耦前提。

验收证据：每个迁移切片可独立构建、验证和回滚，旧/新路径的退出条件明确。

<a id="AM-008"></a>
### AM-008 证据分级评审

将结论分为已验证事实、有根据推断和未验证假设。目录名称只能证明设计意图；编译成功只能证明所纳入目标的代码可构建；硬件时序、并发和故障恢复必须由对应测量证明。

验收证据：每个完成声明都有同层级的命令、日志、静态报告或硬件记录，未验证项单独列出。

<a id="AM-009"></a>
### AM-009 SDK 命名语义归一

1. 收集实际目录、构建分组、公共头和初始化入口。
2. 暂时隐藏 `Core/Device/Driver/BSP/HAL/Platform/Wrapper` 等名称，只读取职责和依赖证据。
3. 按语义层级 ID 标记模块，并记录一对多或多对一映射。
4. 对外部器件继续拆出协议、传输能力、板级绑定和 MCU/OS 实现。
5. 基于语义角色生成依赖规则，不基于字符串路径猜测层级。

验收证据：更换另一厂商 SDK 的目录命名后，角色图和上层依赖规则无需重写，只需更新映射表。

<a id="AM-010"></a>
### AM-010 泄漏基线测量

在提出重构方案前，先用可重复命令测出当前越界数量，作为基线并写入架构说明：

```text
按语义角色统计公共头中的环境类型出现次数
按语义角色统计直接 include 厂商/RTOS 头的文件数
统计全局 include 搜索路径条数
统计同一能力出现在几个不同目录
统计 planned/弱实现占位数量
```

随后对新增代码设零容忍，对存量设定下降目标，并让 [AM-006](#AM-006) 的检查持续输出该基线。

验收证据：基线命令、数值、快照提交号可复现，两次执行差异可解释。

<a id="AM-011"></a>
### AM-011 环境边界分析先行

任何自动检查都建立在一组人类判断之上：什么是厂商代码、什么是用户代码、哪些头属于环境、这个目录想表达什么意图。这些判断脚本做不了，必须先由模型读代码得出，再由人确认。

1. 通读构建配置与目录，区分**自维护代码**与**厂商/生成代码**，依据是来源与可改写性，不是路径名。
2. 找出直接接触环境的文件：include 了厂商 SDK、HAL、寄存器定义或 RTOS 头的，就是环境接触面。
3. 逐个公共头判定环境中立性：它的传递包含链里是否触达环境头、公共 API 里是否出现环境类型。
4. 对每个目录写出一句意图判断，并附判定证据（职责、公共类型、依赖方向、资源所有权）。
5. 把结论落成机器可读映射，记录确认人；未经确认的映射不得作为门禁依据。

验收证据：映射表的每条规则都有 role 与 evidence 两栏；随机抽取一条，能仅凭 evidence 复核出同样的角色。

反例：先假定"某目录名 = 某层"，再让工具按这个假定扫描。工具会忠实地按错误前提给出干净结果，该失效模式记为 SIG-010。

## 推荐组合

```text
新项目：AM-011 -> AM-001 -> AM-002 -> AM-009 -> AM-004 -> AM-003 -> AM-005 -> AM-006
存量项目：AM-011 -> AM-001 -> AM-002 -> AM-009 -> AM-010 -> AM-003 -> AM-007 -> AM-006
每次评审：AM-008
```

方法规定工作顺序，但不预设必须使用哪个模式。模式选择仍需满足对应变化轴和抽象成本。
