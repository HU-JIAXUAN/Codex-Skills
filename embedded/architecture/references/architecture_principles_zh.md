# 嵌入式架构原则

本文件只定义通用判断原则，是本 skill 知识图的根节点，不引用其它规范文件。可执行约束由 `DR-*` 与 `GATE-*` 承担，角色划分由 `SL-*` 承担，分析步骤由 `AM-*` 承担，具体结构方案由 `PAT-*` 承担，本文件都不重复定义。

<a id="AP-001"></a>
### AP-001 架构控制变化

架构的价值不是目录整齐，而是让变化被限制在可预测的边界内。评估一次设计时，优先问：需求变化会触达多少模块、多少执行上下文和多少验证链路。

<a id="AP-002"></a>
### AP-002 一个模块只有一个主要变化原因

“功能相关”不等于“变化原因相同”。策略、设备机制、芯片细节、调度环境和产品配置应按变化来源分开。模块职责可用一句话表达，并能同时列出明确的非职责。

<a id="AP-003"></a>
### AP-003 依赖指向稳定契约

高层策略不应依赖易变实现。稳定契约由使用者需要的语义定义，而不是由供应商 API、寄存器布局或 RTOS 类型反向塑造。

<a id="AP-004"></a>
### AP-004 所有权必须显式

每份可变状态、硬件资源、缓冲区、定时预算和执行上下文都需要唯一所有者。没有所有者的共享资源会演化为隐式耦合；有多个所有者则会演化为竞态和顺序依赖。

<a id="AP-005"></a>
### AP-005 组合集中，使用分散

实现选择、实例构造和依赖注入集中到组合点。业务模块只消费契约，不自行寻找、创建或切换具体驱动。这样可替换性来自组装，而不是遍布全局的条件编译。

<a id="AP-006"></a>
### AP-006 抽象必须覆盖成本

抽象不是越多越好。可以用以下启发式评估是否引入边界：

```text
抽象收益 = 变化概率 × 变化扩散范围 + 可验证性收益 - 新增复杂度
```

当实现唯一、变化概率低且测试替换没有价值时，同一变化域内的直接依赖可能更简单。第二实现和测试替身只是判断收益的线索，不是数量要求。简化的是实现机制与间接层数量，不能借此取消产品策略与环境实现之间的边界；稳定函数接口、静态接线和内联适配同样可以隔离变化，不必使用动态分配或函数指针。

<a id="AP-007"></a>
### AP-007 架构应可执行验证

只写在图和文档里的边界会逐渐失效。关键依赖方向、公共头文件纯度、组件可见性、资源预算和文档拓扑应尽可能由构建、静态检查或测试自动验证。

<a id="AP-008"></a>
### AP-008 架构的三个视图必须收敛

语义视图说明“希望怎样分层”，构建视图决定“谁实际上能依赖谁”，运行时视图决定“谁真正创建、持有和调用谁”。三者必须表达同一组边界。只有目录没有构建接线是愿望；只有构建分组没有对象所有权是静态分类；只有运行时调用能工作却没有稳定契约，则变化仍会扩散。

<a id="AP-009"></a>
### AP-009 名称不授予架构语义

`Core`、`Device`、`Driver`、`BSP`、`HAL`、`System`、`Platform`、`Wrapper` 等名称在不同厂商和团队中含义不同。层级必须根据职责、变化原因、掌握的硬件知识、依赖方向和资源所有权判断；任何目录名都不能自动获得“高层”“可移植”或“已解耦”的性质。

<a id="AP-010"></a>
### AP-010 完成度按证据分级，不按结构声明

目录、命名、接口文件和设计文档只能证明设计意图。构建成功只能证明纳入构建的代码可编译；实时性、并发、功耗和故障恢复必须由对应测量证明。任何“已解耦”“已平台化”“可发布”的结论都必须写明它属于已验证事实、有根据推断还是未验证假设。

<a id="AP-011"></a>
### AP-011 工程投入应能积累为资产

设计当前功能时，同时识别可保留的业务语义、数据契约、算法/协议、验证工具和决策经验，以稳定边界隔离芯片、板卡和调度差异。复用收益来自下一使用者能理解、接入、验证与维护，不来自复制文件数量或公共目录规模。工程开发必须考虑 App 产品流程、规则、状态机和数据模型的保留与复用；实际用法、验证入口及必要限制清楚即可。不为未知项目预建通用框架，也不丢弃有价值的平台特化。

<a id="AP-012"></a>
### AP-012 固化基本概念与不变量，保留情境决策

Skill 沉淀设计能力，不替项目预选完整设计。稳定概念和已知错误可作为判断依据；具体业务、变化原因、边界位置、对象表示、分层与调用组织由当前证据推导。

| 内容 | 处理方式 |
|---|---|
| 基本概念与不变量 | 保留职责、依赖、所有权、类型/单位、生命周期与有效性等含义，以及越权写入、悬空引用等已知错误 |
| 已明确且可可靠机械判断的规则 | 优先复用编译器、已有 lint、构建与测试；避免每次让 LLM 重复检查，不为凑自动化新增碍事流程 |
| 依赖具体业务的架构选择 | 由 LLM 结合用例、变化、约束和成本比较方案，说明为什么此处需要或不需要边界；有不确定性就用最小验证解决 |

示例用于展示怎样思考，不能把字段表、层数、函数表或一次项目经验升级为普遍硬要求。需要保留的是做出选择的理由、适用条件和后续可复用的认识。

## 架构能力模型

学习架构不以记住模式名称为终点，而以以下能力为主线。表中结果用于观察设计效果，不要求逐项生成文件或表单：

| 能力 | 核心问题 | 可观察结果 |
|---|---|---|
| 变化分析 | 什么会独立变化 | 有理由的模块边界 |
| 契约设计 | 调用者真正需要什么语义 | 不泄漏环境细节的公共接口 |
| 所有权设计 | 谁拥有状态、资源与时间 | 唯一 owner 和生命周期 |
| 组合设计 | 谁选择并连接实现 | 单一组合点与显式依赖 |
| 并发设计 | 代码在哪个上下文运行 | ISR/线程/回调约束可见 |
| 验证设计 | 边界如何防止退化 | 相称的检查与可复现实证 |
| 视图对齐 | 声明、构建和运行是否一致 | 受影响边界能够相互印证 |
| 语义归一 | 不同 SDK 名称如何比较 | 按实际职责判断依赖 |
| 对象与数据建模 | 实例、配置、状态和快照怎样共同维持不变量 | 唯一状态来源、数据契约与生命周期 |
| 资产积累 | 本次工程怎样降低下一次接入与验证成本 | 可理解、使用和维护的成果 |

判断一份架构是否成熟，重点看“修改一个变化点需要知道多少无关知识”，而不是看目录层数或模式数量。
